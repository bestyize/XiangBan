# AI 网关与额度系统设计（server-ai）

状态：一期已实现（`services/server-ai`，未部署）；兑换码（二期）和在线支付（四期）尚未实现。本文记录为什么这样设计；接口与配置以 `services/server-ai/README.md` 为准。

与最初设计相比，一期实现有两处不同：试用只发一次由 `quota_buckets` 上「每个绑定只能有一个试用桶」的唯一索引保证，没有单独的 `trial_grants` 表；`usage_snapshots` 表没有做，对账的每次结算直接记在 `quota_ledger` 里。

## 目标与边界

- 为产品矩阵提供统一的 AI 调用能力，第一批接入「小伴壁纸」（网站、桌面、手机三个端）。
- 身份只认账号中心（`server-account`）。上游模型网关用现有的 New API（首尔机，`newapi.thinkbody.xyz`，仅监听 `127.0.0.1:3000`）。
- 额度按**产品隔离**：同一账号在不同产品里余额互不相通，试用额度也按产品各发一次。
- 充值方式：第一期只做**兑换码**（淘宝店卖码）。在线支付（微信/支付宝）等商户号批下来再接，订单层预留扩展口。

不做：账号中心不存任何额度数据（见 [account-center.md](account-center.md)）；产品客户端永远拿不到 New API 的 Key。

## 总体结构

```
产品客户端 ──(账号中心 access JWT)──▶ server-ai ──(产品专属 Key)──▶ New API(127.0.0.1:3000) ──▶ 上游模型
                                          │
                                          ├─ PostgreSQL（独立库 xiaban_ai：账本、码、映射）
                                          └─ JWKS 验签账号中心令牌（离线，不回源）
```

- `server-ai` 部署在首尔机，与 New API 同机，经回环地址调用，管理凭据只存在它的环境变量里。
- 技术栈与账号中心一致：Rust Axum + PostgreSQL（SQLx）。

## 产品与客户端

账号中心里「小伴壁纸」有三个 `client_id`：`xiangban-wallpaper-web`、`xiaoban-desktop-wallpaper`、`xiaoban-mobile-wallpaper`。额度要按**产品**算，所以 `server-ai` 自己维护「产品 → 客户端列表」的映射，由令牌 `aud` 查出产品；`aud` 不在任何产品里则拒绝。同一个账号在三个端共用壁纸产品的一份余额。

## 数据模型

| 表 | 内容 |
| --- | --- |
| `products` | `product_id`、名称、`client_ids[]`、试用额度（点数）、试用有效天数、是否启用 |
| `product_tiers` | `(product_id, tier)` 唯一；`tier` 是客户端可见的档位名（如 `standard`、`premium`）、展示名、简介、对应的真实模型、`requires_paid`（是否要求有付费桶）、`is_default`（客户端未指定档位时使用）、排序、是否启用。档位数量不固定，管理员可随时增删 |
| `product_bindings` | `(uid, product_id)` 唯一；`id`（序号，用于生成 New API 用户名 `ai<id>`）、`newapi_user_id`、`newapi_key`（主密钥派生密钥加密存储）、`synced_quota`（我们认为 New API 当前应有的额度）、状态 |
| `quota_buckets` | 额度桶：`binding_id`、`kind`（trial/monthly/topup）、`total`、`remaining`、`expires_at`、`source`（兑换码 id 或试用） |
| `quota_ledger` | 只追加流水：发放、消耗、过期、作废、管理员调整，带 `bucket_id`、变动值、前后余额，方便对账和退款 |
| `redeem_batches` | 批次：产品、类型、面额、有效期、数量、备注（对应淘宝商品） |
| `redeem_codes` | `code_hash`（唯一）、`batch_id`、状态（unused/redeemed/void）、兑换人 `uid`、兑换时间 |
| `trial_grants` | `(uid, product_id)` 唯一，防重复领取 |
| `usage_snapshots` | 每次同步的读数与差值，排查异常用 |

额度单位直接用 New API 的点数（500000 点 = 1 美元），避免换算误差。展示给用户时再换算。

## 额度桶规则

- **试用**：用户首次调用某产品 AI 时发一个桶（金额、有效期取自 `products`）。`trial_grants` 的唯一约束保证只发一次。
- **月卡**：兑换后生成 30 天有效的桶，到期未用完的部分作废。多张月卡各自独立计时，不顺延。
- **加油包**：长期型桶，有效期 1 年，不做永久。
- **扣费顺序**：先扣最早过期的桶，同时间过期则先扣小面额的。
- 可选：月卡每日消耗上限（占总额百分比），默认关，做成产品配置项。

## 档位

客户端只认档位名，不接触真实模型名。初期两档：

- `standard`（标准）：试用用户可用。
- `premium`（高级）：`requires_paid = true`，调用时要求绑定下至少有一个未过期、剩余大于 0 的**付费桶**（月卡或加油包）；只有试用桶时返回 403，提示兑换。

档位到真实模型的映射只存在 `product_tiers`，换上游或调整成本只改后台配置，不用给桌面和手机包发版。余额不按档位拆分：New API 按模型倍率扣额度，高级档自然消耗更快。

已知局限：New API 里用户钱包只有一个数字，分不出试用与付费额度。试用用户兑换付费码后，高级档可能花掉剩余的试用额度。这点接受，不为它增加同步复杂度。

### 管理员配置

管理后台提供档位管理，管理员可以：新增、停用、排序档位；修改展示名与简介；为每个档位选择真实模型；设置是否要求付费、哪个是默认档。用户和客户端永远看不到真实模型名，包括响应、错误信息和 `GET /api/ai/tiers`。

保存档位时，`server-ai` 会读取 New API 的模型列表做校验：

- 模型不在 New API 已启用的模型里，拒绝保存，避免配出一个必然失败的档位。
- 模型的倍率与 New API 的默认值相同，保存时给出警告，提示可能未配置真实定价，仍允许保存。
- 修改只影响之后的新请求，在途请求不受影响；每次修改写入审计日志，记录旧值、新值和操作人。

选择与展示由客户端决定：客户端调用 `GET /api/ai/tiers` 拿到可用档位，要给用户选档位或只用默认档，是前端产品决策，后端两种都支持。

## 与 New API 的同步

每个 `(uid, product)` 在 New API 对应一个独立用户（用户名 `ai<binding_id>`，长度远小于上限 20；密码为随机 32 位，永不用于登录）和一个**无限额度**的令牌。令牌不限额，实际只扣用户钱包，限额完全由用户额度决定。

New API 里的用户额度由 `server-ai` 通过 `POST /api/user/manage`（`add_quota`，`mode` 为 `add` 或 `subtract`）维护。**一律用增减，不用 `override`**，因为增减是原子的，不会和在途请求互相覆盖。

同步任务（每分钟，按绑定逐个处理）：

1. 读 New API 当前额度 `actual`。
2. `consumed = synced_quota - actual`，按扣费顺序从桶里扣减，写流水，然后 `synced_quota = actual`。
3. 处理过期桶：把剩余值算作过期，对 New API 做 `subtract`（上限为当前 `actual`，不让它变负），同时 `synced_quota -= 已减值`，写流水。
4. 兑换、试用发放等入账动作在同一数据库事务里更新桶与流水，再对 New API 做 `add`；失败则标记待重试，由同步任务补做。
5. `consumed < 0`（New API 额度比预期多）说明有人在 New API 后台手动加过额度，记录异常并告警，不自动处理。

已知误差：桶过期到被同步清掉之间，最多相差一个同步周期，用户可能多用一点额度；单次请求的实际花费可能略超余额（New API 先预扣再结算）。两者都由我们承担，量级是一次调用的费用，可接受。

## 调用代理

`POST /v1/chat/completions` 等 OpenAI 兼容路径：

1. 用 JWKS 验签账号中心令牌，校验 `iss`、`exp`，由 `aud` 查出产品；查不到或产品停用则拒绝。
2. 取 `sub` 与产品对应的绑定；没有就懒创建（建 New API 用户、建令牌、发试用桶），用 `(uid, product)` 唯一约束和数据库锁防止并发重复创建。
3. 未过期桶总额为 0 时直接返回 402，提示兑换。
4. 请求里的 `model` 字段填档位名（如 `standard`）。按 `(product, tier)` 查 `product_tiers`：不存在或已停用返回 400；`requires_paid` 但没有付费桶返回 403。
5. 把请求体里的 `model` 改写成真实模型，用该绑定的 Key 转发到 New API，原样透传流式响应，不缓存响应体，日志里不记录提示词和回复内容。响应里的 `model` 字段不回写真实模型名，保持档位名；上游返回的错误信息先过滤，把其中的真实模型名替换回档位名，只返回通用错误码和提示，避免泄露上游信息。`GET /v1/models` 也只返回档位名。
6. 令牌上**不设**模型限制。档位到模型的映射会在后台随时改，若令牌带着旧模型列表，换模型后所有已建令牌都会失效，批量改又要逐个调 New API。令牌只存在于 `server-ai` 里、New API 只监听回环，模型范围由代理层这一道检查把关即可。

## 兑换码

- 码格式：`XXXX-XXXX-XXXX-XXXX`（去掉易混淆字符），最后一位为校验位，输错先在本地拦住。
- 数据库只存哈希；明文只在生成批次时导出一次（CSV，用于淘宝自动发货的卡密库存），之后无法再查。
- 兑换必须登录；码绑定产品，不能跨产品使用；一次性。兑换接口按用户和 IP 限流，防止乱猜。
- 兑换在单个事务里完成：码状态改为已兑换、生成桶、写流水，要么全成功要么全失败。
- 淘宝退款：未兑换的码在后台作废；已兑换的码可在后台把对应桶扣回（写流水，不删记录）。

## 对外接口

| 方法 路径 | 鉴权 | 说明 |
| --- | --- | --- |
| `GET /api/ai/tiers` | 用户令牌 | 当前产品的档位列表：档位名、展示名、当前用户是否可用（不返回真实模型名） |
| `GET /api/ai/balance` | 用户令牌 | 当前产品各桶剩余、过期时间、合计 |
| `POST /api/ai/redeem` | 用户令牌 | `{code}`，兑换到令牌 `aud` 所属产品 |
| `GET /api/ai/ledger` | 用户令牌 | 分页流水 |
| `POST /v1/chat/completions` 等 | 用户令牌 | 代理 |
| `GET /api/health` | 无 | 健康检查 |
| `/api/admin/*` | 独立管理员令牌 | 产品配置、批次生成与导出、作废码、扣回桶、查看用户余额与异常 |

管理员体系沿用账号中心的做法：独立表、独立签名密钥、没有默认账号。

## 对 New API fork 的改动

只做一处，其余用现有接口：

- 新增 `POST /api/user/:id/token`，管理员代指定用户创建令牌，返回 Key。要求 `user:write` 作用域；创建的令牌固定为无限额度，不设模型限制。
- 必须在 `middleware/access_token_routes.go` 里为新路由声明作用域规则，否则按该 fork 的约定会被拒绝（默认关闭）。
- 管理员账号：新建一个专用管理员，只授予 `user:read`、`user:write` 的访问令牌，不使用 root。
- 先在本地编译、上传到首尔机替换；这是生产网关，部署前需要你确认时间窗口，并保留旧二进制作为回滚点。

## 上线前检查清单

- 确认线上 New API 的「新用户注册额度」（`QuotaForNewUser`）为 0，否则每个新绑定用户都会白送额度。代码默认值是 0，但它是可配置项，需要查线上设置。
- 确认专用管理员令牌的作用域只含 `user:read`、`user:write`。
- 小伴壁纸的试用额度和有效期已定：0.5 美元（250000 点）、7 天，后台可改。
- 两个档位各对应的真实模型需要你给定，且这些模型必须已在 New API 里配置好渠道并确认可用。初定 `standard` 用 DeepSeek，`premium` 先用 Claude，后台可随时改。
- **每次在后台换模型，都要先到 New API 核对该模型的倍率已配置**。线上现状：公开价格接口里 17 个模型的倍率全是 37.5，DeepSeek 和 Claude 都一样，这很像未配置时的默认值，而不是真实定价（尚未在 fork 源码里确认）。按默认值计费会与真实成本相差很大，上线前必须为用到的模型逐个配置倍率。这一条也适用于淘宝上码的面额定价：按高级档的实际成本核算。
- 法务与合规（算法备案、淘宝对 AI 类虚拟商品的规则）不在本设计内，由你自行评估。
