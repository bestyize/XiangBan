# 统一账号中心设计

实现位于 [services/server-account](../../services/server-account/README.md)。本文记录为什么这样设计；接口、配置和运行方式以该 README 为准。

## 目标与边界

- 一个相伴账号在所有产品（壁纸网站、桌面/手机壁纸、主 API 及后续应用）通用。
- 账号中心只管：身份（邮箱/手机号）、基本资料（昵称、头像）、登录凭证与会话。
- 账号中心不管：游戏钱包、收藏、下载记录等业务数据，管理员账号（各服务的 `admin` 仍是独立的运维账号）。

## 模型

借鉴微信/QQ 的分层：

- `users.uid`：全局唯一用户 ID，不可变，作为令牌 `sub`。
- `identities`：一个用户可绑定多种登录标识，当前为 email、phone，每类最多一个；以后加微信、QQ 只需新增 `kind`，不改用户表。
- `clients`：登记的应用（令牌 `aud`），用于区分来源设备/产品、按应用吊销会话。
- `refresh_tokens`：按令牌族管理的设备会话。

### 为什么 `sub` 用全局 uid，而不是按应用隔离的 openid

微信用 openid（每应用不同）加 unionid（全局）来防止第三方应用互相关联用户。这里所有产品同属一个团队、一套数据治理，隔离带来的收益小，却会让跨产品的数据合并（例如游客账号并入正式账号）变复杂。因此 v1 直接用全局 `uid`。若以后要开放给第三方应用，再在令牌里增加按应用派生的 `sub`，业务侧只依赖 `sub` 不透明字符串即可平滑切换。

## 登录与令牌

- 验证码登录即注册：验证通过后标识符视为已验证，不存在则创建用户。
- 令牌：access JWT（EdDSA，30 分钟）+ 不透明 refresh token（30 天，一次性轮换）。业务服务用 JWKS 公钥离线验签，不回源账号中心、不共享密钥。
- 刷新令牌被重放（已作废的令牌再次出现）时整个令牌族吊销，应对令牌泄露。
- 选择自研而非 Keycloak/Casdoor/Logto：范围只有验证码登录，国内短信通道需要自写适配，而仓库已有 Rust Axum + PostgreSQL 的成熟写法；对外保持标准 JWT/JWKS，以后迁移到现成 IdP 时业务服务无需改验签逻辑。

## 安全取舍

- 短信接口最容易被刷：每标识符 60 秒冷却与日上限、每 IP 日上限；上线前仍建议在前端发送前加人机验证（如腾讯云天御验证码），服务端目前未集成。
- 重置密码接口不暴露账号是否存在；密码登录对不存在账号做等耗时校验，错误信息统一。
- 标识符存哈希 + 密文，库泄露不直接暴露邮箱/手机号；主密钥必须与数据库分开备份。

## 管理后台

后台随账号中心同一个进程托管（`/admin/`），不单独部署：账号数据只有这一个服务能读，后台直接走同库查询，比再开一套服务经接口转一圈简单，也少一个对外暴露面。

- 管理员单独建表，不和用户混在一起；令牌用主密钥派生的 HS256 密钥签发，与用户 EdDSA 令牌完全不通用。即使业务服务拿着 JWKS 公钥也无法验证或伪造管理员令牌，反之用户令牌打不开后台接口。
- 没有任何默认账号：首次启动由环境变量创建初始管理员，之后环境变量被忽略。避免出现 `admin/123456` 这类默认口令上线。
- 能做的事刻意收窄：看用户和掩码后的标识、停用/启用、下线设备、管理应用、看发码统计和操作日志。看不到验证码，也看不到完整邮箱/手机号（只能用完整号码精确查找），降低管理员侧的隐私风险。写操作全部入审计表。
- 停用用户会立即吊销刷新令牌，但已发出的访问令牌无法撤回，只能等其过期（默认 30 分钟）。要做到即时生效，需要业务服务每次回源校验，成本和复杂度都更高，v1 不做。

## 与现有系统的关系

- 主 API 现有的游客账号、钱包合并等业务规则留在主后端。迁移时给主后端用户表增加账号中心 `uid` 映射，登录后用 `uid` 触发既有合并逻辑，不改合并规则本身。
- 壁纸站的用户功能（若需要）直接依赖账号中心令牌；其管理员 Session 保持不变。
- 本次只实现账号中心服务本身，尚未改动任何现有产品去接入它。
