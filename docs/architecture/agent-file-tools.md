# 统一聊天附件与文件分析架构

日期：2026-10-20。状态：第一版实现。

## 决策

采用少量通用工具、独立文件能力包和按需 Skill。放弃把全部附件协议与解析器塞进 agent-kernel，也不为每一种格式注册独立工具。

| 层 | 责任 |
| --- | --- |
| agent-kernel | 工具执行、模型协议、权限、上下文预算及现有多模态工具结果 |
| agent-file-tools | 通用 read_file 扩展、基础文档提取、会话附件副本、消息元数据桥接、分析 Skill 与辅助脚本 |
| 小伴桌面 | 文件选择/拖放/粘贴/截图、附件卡片、IPC、存储位置、运行与删除生命周期 |
| 原有 Shell | 在当前权限规则下执行复杂统计、转换等脚本 |

工具包统一归档在 `libs/agent-tools/` 下，文件能力位于 `libs/agent-tools/files/`，crate 名称仍为 `agent-file-tools`。后续工具类型按独立子包扩展，避免聚合全部依赖。

依赖方向为小伴桌面 → agent-file-tools → agent-kernel。Kernel 源码保持不变。其他产品可以注册同一扩展工具、提供自己的存储目录，不需要重新实现解析器。

## 数据流程

1. 两个聊天入口共用 attachments.ts；图片保留兼容的 data URL，文档携带名称、大小与 data URL。
2. chat_send 验证消息数量与大小，把图片和文档都导入 chat/attachments 下的会话目录。实际文件名由随机 ID 生成，不使用显示名称拼路径。
3. 图片继续通过原有 Part::Image 发送；文档只提供资源元信息，由 Agent 调用 read_file 按需读取。
4. AttachmentHistory 在 JSONL 的普通用户消息 structured_content 中写附件元数据，旧消息无此字段时仍可用。
5. AttachmentContext 在每次请求副本中加入可信宿主生成的附件清单，运行于 ContextTrim 之前。文件名与内容仍标为不可信数据。
6. read_file 校验规范化路径，允许工作目录、spill 和当前会话附件目录，返回文字、图像或错误。
7. 复杂计算通过 Skill 指导使用现有 Shell。Skill 附带 CSV 精确求和脚本，先检查解释器/库，不偷偷安装依赖。
8. UI 乐观显示附件卡片；发送拒绝时恢复整个草稿；重启后从保存的元数据重建卡片。重试复用原消息及原附件。
9. 运行前失败、线程创建失败、取消且尚未保存消息时回收新导入文件；已写入历史的附件保留。会话删除时清理该会话文件。

## 第一版支持与边界

- 图片：PNG/JPEG/GIF/WebP。仍需要模型本身具备视觉能力。
- 文本：UTF-8 文本、代码、CSV、日志等。CSV 默认文本读取；精确计算用脚本。
- PDF：文字层提取。不能保证扫描页、插图、复杂排版完整覆盖。
- DOCX/PPTX：正文/幻灯片文字，附来源位置；不做排版渲染。
- XLSX：工作表与单元格缓存值；不重算公式、执行宏或外链。
- 限额：每条 8 个附件；单文件 10 MiB，图片 3 MiB，合计 30 MiB。
- JSONL 继续保存原有内联图片，第一版未消除 base64 历史体积。
- 格式解析依赖都属于外部能力包；基础读取无需安装 Python。
- Shell 不是沙箱，附件目录校验不能限制 Shell 对其他目录的访问。
- 不自动换模型，不接外部 OCR，不自动安装 Python/依赖。
- 解析器仍在进程内运行；PDF 库调用期间无法硬中止，不能把内核线程超时描述成资源隔离。
- 尚未实现生成文件的独立下载卡片、解析缓存、缺失附件状态检查及旧文件重新关联。

## 后续扩展条件

先依据真实任务决定是否增加 PDF 页面渲染、OCR 和受管 Python 环境。只有进程资源消耗或隔离需求出现后，再把解析放进可终止 worker。新增格式优先扩展 read_file 背后的适配器；稳定的高频复杂操作可作为 Skill 辅助脚本，不默认增加模型工具。

## 验证入口

- 独立 Rust 包测试覆盖实际 PDF、DOCX、PPTX、XLSX 读取、图片结果、会话路径范围、失败回滚、历史与 Agent 工具循环。
- 前端对附件读取、混合发送、历史恢复和两个聊天入口做定向测试，并执行 vue-tsc。
- 桌面原生构建需目标平台系统依赖；Linux 缺少 pkg-config/GLib 时无法完成 Tauri 原生检查，不能据此宣称 macOS/Windows 实机已验收。
