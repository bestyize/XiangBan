# Agent 框架现状审视与演进设计

审视日期：2026-10-19。范围：`libs/agent-kernel` 及 `client/xiaoban-desktop-wallpaper/src-tauri/src/chat` 的当前工作区代码，包含未提交改动。本文区分现有实现与建议，不表示后述接口已经实现。

实施进展（2026-10-20）：第一阶段已接入 0.2.0，包含 Schema 注册/调用校验、保守工具默认值、保留错误/JSON/图片的结果链路、MCP 环境白名单与结果来源、专用摘要记录，以及包含工具定义和输出预留的上下文预算。0.3.0 完成阶段 B 的基础：运行身份与序号、可失败观察者、独立执行日志、调用预算、进程会话、结束清理与父子身份链，桌面同步接入，独立 stdio 参考宿主可按需启用进程工具。下文“当前具体缺口”保留审视时的事实；阶段 B 尚未完整完成，跨进程会话租约、持久任务恢复和共享预算仍待实现，Provider 推理元数据与第二宿主真实任务验收也未完成。已实现架构与限制见 [运行与进程基础](agent-runtime.md)，验证与兼容性说明以 [内核 README](../../libs/agent-kernel/README.md) 为准。

## 定位与结论

建议定位为：**可嵌入、可观察、可控制的 Rust Agent 执行框架**。桌面开发助手是参考宿主之一，服务器助手、其他桌面产品也可以接入；框架不承担具体产品业务，不要求所有宿主提供 shell、电脑控制或开发环境。

当前是一个已经处理了不少真实边界情况的轻量执行内核。值得继续演进，不需要推倒重写。但还不是一个在模型协议、任务恢复、安全边界、跨平台验证和发布契约上完备的公共框架。

优先顺序：可靠执行与结果保真 → 明确扩展边界 → 长任务与开发体验 → 第二个独立宿主验收 → 公开发布。

## 已有能力与值得保留的设计

| 能力 | 代码事实 | 评价 |
| --- | --- | --- |
| 产品隔离 | `ModelProvider`、`Tool`、`SessionStore`、`Middleware` 由宿主注入；内核不依赖 Tauri | 最重要的基础，应保留 |
| 依赖与功能选择 | 默认仅 serde/serde_json，网络、文件、skills、MCP 等按 feature 开启 | 适合嵌入，不必为追求统一引入大型运行时 |
| 执行闭环 | 工具失败回传模型，流式文本、重试、取消、并行与串行工具均有实现 | 已经超过简单的模型工具调用示例 |
| 历史完整性 | 中断后补缺失工具结果；截断工具调用不执行；受限的 `retry_last` 避免重复已落盘动作 | 处理方向正确；仍需进一步区分历史修复与外部动作恢复 |
| 存储 | MemoryStore、JSONL、格式版本、尾部半行恢复、Unix 文件权限 | 轻量存储可保留；不能据此承诺跨进程并发与持久任务 |
| 输出与上下文 | 大输出落盘、按整轮裁剪、保留调用与结果对应关系 | 比直接截断字符串更可靠 |

| 文件工具 | 读取分页、写入原子替换、精确编辑、路径与符号链接检查 | 适合基础代码编辑；文件工具范围不等于进程沙箱 |
| Skills 与记忆 | 按需加载技能正文，自创技能有备份和来源字段，笔记独立存储 | 可复用；需要补宿主信任来源与权限边界 |

| 测试方法 | ScriptedProvider、本地假 HTTP 服务覆盖协议和边界 | 确定性回归是优势；真实模型任务效果需另设验收 |

## 当前具体缺口

### 1. 工具契约与默认值：优先修复

`src/exec.rs::prepare` 解析参数 JSON 后直接进入中间件与工具，未统一按 `ToolSpec.schema` 校验。内置工具分别做了部分字段检查，但第三方接入不能依赖这种约定。

`ToolSpec::new` 默认 `Risk::Read`、`parallel_safe = true`，遗漏配置会把写操作或非线程安全操作当作只读、可并行。供外部使用时应要求显式声明，或提供保守默认值与开发期告警。

建议：明确支持的 Schema 子集；工具注册时校验定义，调用前校验参数；错误返回字段路径和原因。发布迁移说明，避免无提示改变现有工具行为。

`ToolResult` 有 `is_error`，但 `run.rs` 写入历史时只保存输出文本，`Message` 没有工具错误字段。错误语义会在历史和 Provider 转换中丢失。应使用结构化工具结果，保留状态、错误码、可重试性、正文及产物引用。

### 2. 多模态结果与 Provider 协议：优先修复

消息支持文本与用户图片，但工具接口返回 `Result<String, String>`；`mcp.rs::call_tool` 把图片转成 `[image: ...]` 文字，未保留 `structuredContent` 等结果。这会使截图工具“调用成功但模型看不到图片”。

建议先实现文本、图片、结构化 JSON 与文件引用的结果块，保留 MIME、大小和来源；大文件由 ArtifactStore 管理，不直接塞进每轮上下文。Provider 按实际能力编码，不支持的类型显式报错或受控降级。

Responses 的 reasoning items、phase，以及 Claude thinking 等必要回传内容尚未完整保留，当前 README 已披露相关限制。应增加 Provider 专属的不透明元数据和能力声明，确保同协议历史可往返；不把内部推理内容默认暴露给 UI 或日志。切换 Provider 时进行兼容性检查，不假设任意历史都能无损转换。

不要把所有兼容性都交给 `extra_body`：工具、图片、上下文窗口、输出额度、协议扩展等应有可检查配置。对未支持的思考模式明确拒绝，避免请求能发出但后续工具循环不正确。

### 3. 长任务与进程生命周期：优先建设

当前 Shell 默认 120 秒，stdin 关闭，结束时一次性返回输出，没有可继续交互的进程会话。调大 timeout 无法解决开发服务器、长编译、分段日志和后续输入。

建议新增可选进程模块：start、poll/read、write、stop；进程句柄归属 workspace/session/run；记录退出码、输出偏移和最后活动时间；分别设置执行时限、空闲时限、输出上限和生命周期。交互终端作为可选后端，不要求普通命令都开 PTY。

通过 ExecutionBackend 抽象本地、受限进程、容器或远端执行。同一任务的文件工具和进程工具必须指向同一工作区；取消时清理受管子进程，禁止把“停止等待结果”当作“动作已经停止”。

同步加线程可以继续保留；先补并发上限、队列、资源回收和边界。`exec.rs` 目前每个并行调用创建线程，没有统一并发额度；超时只对不配合取消的工具发信号，不能强制终止其副作用。需要隔离时使用进程或远端执行边界。

HTTP 读取阶段已有取消检查，但 `http.rs` 在响应流处理前执行阻塞 `.send()`，取消与总 deadline 尚未贯穿所有阶段。应覆盖连接、等待响应头、读取与重试，并限制读取通道和帧大小。

### 4. 任务状态、恢复与副作用：优先建设

当前核心接口是阻塞式 `run` 和即时事件回调；主要存的是消息，而非持久运行记录。stdio 有 run id 包装，但核心 Event 没有统一 run/parent/序号信息。`Agent.running` 只约束同一个实例，不能阻止两个 Agent 实例或两个进程同时修改同一会话。

建议引入 RunRecord、事件序号与 SessionLease；提供事件订阅、断线补读、取消、暂停、恢复及稳定终态。等待用户与等待批准应可持久化；崩溃后原批准是否有效由明确规则决定。

建议状态：queued、running、waiting_for_user、waiting_for_approval、paused、succeeded、failed、cancelled、interrupted。模型 FinishReason 与任务状态分开，模型不调工具不能等同于业务任务通过验收。

外部动作已发生而结果未落盘时，补一条 interrupted 工具消息只能修复对话结构，无法判断动作是否执行。工具元数据应区分只读、幂等、可通过业务键去重、不可重放；恢复时对不确定动作进行状态核对或人工处理，不自动重放。不要承诺任意外部工具的 exactly-once。

### 5. 上下文与压缩：优先修复正确性，再抽取

ContextTrim 只估算消息，不包含工具 Schema，也未统一预留输出预算。当前单轮超过预算时会保留并交给 Provider 判断，测试明确覆盖此行为，因此不能宣传“始终保证请求在窗口内”。

建议预算公式覆盖系统提示、工具定义、历史、当前输入、Provider 元数据、输出预留与安全余量；实际使用量用于校准。单轮无法容纳时返回结构化原因，选择分块、文件引用或压缩，不默默发送超限请求。

模型摘要目前在桌面 `chat/compact.rs`，属于值得复用的能力，适合抽成可选 ContextPolicy/compaction 模块。压缩要能在长 run 的安全边界发生，而不仅回答结束后发生。保留目标、约束、决定、未完成工作、产物引用与动作状态；原历史继续留存。

当前摘要通过普通 user 消息中的 `[[xiaoban-summary ...]]` 标记识别，没有专门的受信记录类型。用户输入完整匹配标记即可被当作摘要。应改为独立的宿主记录类型，避免控制信息与用户正文混用；不要把摘要内容提升为系统授权。

### 6. 权限与隔离：优先明确契约

现有读写/网络/执行风险、批准与污染跟踪很实用，但不足以描述“只能改这个目录”“只能访问这些域名”“能读文件但不能外传”。`danger_check` 是宿主命令启发式；安装后 Auto 会跳过 taint 与 always_ask 的强制询问。这是当前产品选择，框架应让这种策略显式可见，不能称为隔离。

建议将权限拆为宿主策略、工具资源需求、已授予范围与执行后端约束。资源范围包含读/写路径、目标服务或域名、执行程序、凭据与有效期；批准可绑定具体动作和范围。子 Agent 的权限不得超过父任务授权。服务端通常需要策略拒绝，不应强制要求交互弹窗。

shell 清理环境变量是优势，但仍继承 HOME 等，进程保留当前用户权限，仍可能读取文件凭据。MCP 启动目前没有 env_clear，会继承宿主环境；需统一环境白名单、按服务注入凭据与日志脱敏。MCP 结果也需明确来源与信任策略，目前包装工具未默认设置 untrusted_output。

持久授权、污染和恢复规则应一致；不要让重启意外改变安全语义。第三方工具自身是可执行代码，安装信任与运行参数批准是两个不同层面。

### 7. MCP、Skills 与扩展边界：逐步完善

MCP 目前是固定协议版本的 stdio 客户端，一次 tools/list。建议先补版本/能力协商、分页、工具列表变化、取消通知、结果块、帧大小限制、可控 stderr 与断线状态。远程 HTTP 传输和认证按实际接入需求追加，不要求首次开源就实现全部 MCP 能力。

Skills 是指令包，不应成为绕过宿主权限的入口。`origin: agent` 是文件内容字段，适合作为管理约定，不宜作为可信安全凭证。记录宿主认可的安装来源与版本；自修改、自安装按策略控制。

框架可提供项目指令加载器，宿主决定是否启用 AGENTS.md 等约定。需明确根目录、层级、作用范围、可信来源和缓存失效；不能简单把仓库所有文档拼进 system prompt。

子 Agent 已有单次委派、事件观察与清理钩子，但用量不计入父级，权限靠宿主自行装配。应先补共享预算、身份链、取消与权限收缩；持久子任务、多人协作和共享工作区冲突管理后置。桌面当前 assemble 未注册 Subagent，不能把内核支持等同于桌面已启用。

### 8. 预算、可观察性与效果验收：发布前补齐

max_turns 只限制模型轮数；Usage 只有输入/输出 token，没有父子共享预算、总耗时、工具数量或并发限制。建议按 run 建立可组合 Budget，父子共享配额；缓存 token 等用量细节由 Provider 提供。金额预算依赖宿主价格与模型路由，未知用量不能当零，也不能保证估算金额等于账单。

建议事件包含 run_id、session_id、parent_run_id、序号、时间、状态与错误码；可选 TraceSink 记录耗时、重试、脱敏请求摘要、权限决策和产物引用。具体监控系统作为适配器，不硬编码进循环。

确定性测试之外增加人工手动触发的真实端点兼容测试，以及真实任务集：读改现有项目、修复失败测试、长命令取消、MCP 截图、工具执行后中断、上下文溢出、权限拒绝、Windows 路径与进程树。记录完成率、错误副作用、耗时、token、人工介入次数和恢复成功率，建立基线后再设门槛。

## 建议的职责分层

| 层 | 内容 | 不放入这一层的内容 |
| --- | --- | --- |
| Core | 消息/结果/事件契约、run 状态、循环、取消、预算、调度、恢复协议 | Tauri、产品人设、下载地址、UI |
| 可选通用模块 | Provider、文件/进程、MCP、skills、memory、compaction、存储与追踪适配 | 某个产品业务与账号策略 |
| 开发环境库 | Python/Node 检测、版本、下载校验、缓存、项目虚拟环境、执行环境配置 | Agent 决策循环与具体页面 |
| 宿主与产品 | 工具装配、工作区、凭据来源、权限策略、UI、产物打开方式 | 重复实现通用循环和历史恢复 |

以上是逻辑分层，近期继续使用一个 crate 加 feature/module 即可。只有依赖、平台构建或发布节奏确实不同再拆 crate；开发环境管理适合独立库，避免内核必须包含下载器与所有平台安装逻辑。

建议先稳定少量扩展点：ExecutionBackend、ContextPolicy、RunStore/SessionLease、ArtifactStore、Policy、EventSink。名称是设计建议，不要求一次性建出全部 trait。先从一个真实需求抽取，防止形成没人使用的抽象。

第三方最小接入目标：提供模型、存储和一个自定义工具即可运行；按需选择权限及执行能力。Rust 直接调用，其他语言先通过已有 stdio 协议接入，再提供薄层 TypeScript/Python 客户端，统一事件和取消语义。

## 分阶段实施与验收

| 阶段 | 建设范围 | 验收标准 |
| --- | --- | --- |
| A：契约与正确性 | Schema 校验、保守工具默认值、结构化错误/结果、MCP 图片与环境隔离、摘要记录类型、上下文预算 | 非法参数不执行；错误语义落盘往返保留；图片能送到模型；宿主未授权环境变量不进入 MCP；正文不会变成控制记录 |
| B：执行可靠性 | 进程会话、统一事件标识、持久状态、会话租约、取消与 deadline、父子预算 | 长构建可分段观察；取消能清理受管进程；重启能报告中断状态；不盲目重放外部写动作；多个实例不并写同一会话 |
| C：协议与开发能力 | Provider 元数据与能力、通用压缩、项目指令、独立运行时库、产物打开协议 | 同协议历史保真；不支持配置明确拒绝；干净机器能准备选定运行时并完成限定开发任务；原项目规范有效 |
| D：复用与发布 | 无 Tauri 的第二个宿主、跨语言示例、平台矩阵、版本与迁移政策、LICENSE、发布配置与文档 | 外部开发者按说明可运行；旧会话/协议有升级或明确拒绝策略；测试覆盖声明的平台与 feature 组合 |

目前 Cargo.toml 为 0.1.0、publish=false，尚未声明 license、rust-version 等公共发布信息；内核 README 仍有“尚未接入任何产品”的过时陈述，与桌面实际接入不符。正式发布前应统一能力矩阵、已验证平台与示例，避免文档承诺超过实现。

所有现有或未来 GitHub Actions 均仅允许 workflow_dispatch，不引入自动 CI、自动发布或定时评测触发器。

暂缓建设：完整 IDE/LSP、自研容器平台、分布式工作流引擎、插件市场、复杂多 Agent 编排、无依据的向量记忆。先用参考宿主证明稳定完成任务，再依据实际瓶颈增加。
