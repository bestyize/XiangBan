# 任务单 D：模糊测试与加固

这份任务单**自包含**：不需要读仓库其余部分，但需要拿到仓库代码（要改的三个目录在 §2）。产出是对**已合入的三个组件**的健壮性测试，以及对发现的问题的**最小修复**。目标不是增加功能，而是证明“拿到恶意或损坏的输入，这些组件不会 panic、不会卡死、不会吃光内存或 CPU”。

## 1. 背景

这三个组件都会处理来自不可信一方的字节：

| 组件 | 目录 | 不可信输入来自谁 |
| --- | --- | --- |
| 本机语音服务 | `libs/voice-service` | 本机上任何进程（带令牌）上传的音频、JSON、multipart、MCP 请求 |
| 互联协议库 | `libs/link-protocol` | 中转或对端设备发来的信封、二维码内容 |
| 中转服务 | `services/server-link` | 任意已登录设备通过 WebSocket 发来的帧 |

已有的测试覆盖了“正常输入和已知的坏输入”，但**没做过模糊测试和压力测试**（语音库的验收记录里明说了“所有损坏/罕见编码输入及模糊测试”未测）。

## 2. 范围与规则

- 可以新增：各库的 `tests/` 下的测试文件、`fuzz/` 目录（可选）、`dev-dependencies`（如 `proptest`，只能放在 dev-dependencies）。
- 可以修改：上述三个目录里的**源码**，但仅限**为修复本任务发现的问题**所需的最小改动；每处修改都要有对应的回归测试，且在交付说明里逐条说明。**不要**重构、改接口、改协议。
- 不要改 `libs/link-protocol/vectors/v1.json`，也不要改任何影响协议字节的行为。
- 不要新建 GitHub Actions 工作流（仓库规定所有工作流只能手动触发）。
- 默认用 `proptest`（稳定版 Rust 即可跑）。`cargo fuzz` 需要夜间版工具链且不支持 Windows，作为**可选**项：若提供，放在各库的 `fuzz/` 里并在 README 说明如何运行。

## 3. 目标一：`libs/voice-service` 的输入解析

### 3.1 音频解码 `audio::decode(&[u8]) -> Result<Pcm, VoiceError>`

支持 WAV（PCM16/24/32、float32）、MP3、FLAC、OGG Vorbis；其余返回 415 类错误；**解码后最长 10 分钟**，超过返回 `TooLong`。

测试内容：
- **随机字节**：完全随机、以各格式魔数开头（`RIFF....WAVE`、`fLaC`、`OggS`、`ID3`、`0xFF 0xFB`）的随机尾部、对夹具做随机翻转/截断/拼接/重复（夹具在 `libs/voice-service/tests/fixtures/*.b64`，base64 解码后得到小的真实 mp3/flac/ogg）。要求：**不 panic、不死循环**，每次调用在合理时间内返回（给单次调用设 2 秒上限，用线程加超时检测）。
- **头部谎报**：WAV 的数据块长度写成 4 GB 但实际只有几十字节；采样率写成 1、384000、0、`u32::MAX`；声道数 0、9、65535；位深非法；FLAC 的 `streaminfo` 谎报采样总数；OGG 页的 `segments` 数与实际不符。要求：返回错误或正常处理，**不能按谎报的大小预分配内存**。
- **时长上限**：恰好 10 分钟（边界）、10 分钟加 1 个采样；各种采样率下的计算不溢出。
- **属性**：对任何合法的短音频，`decode` 的输出长度等于 `round(输入帧数 × 16000 ÷ 采样率)`；输出每个采样都在 -1..=1 且有限；对不高于 16 kHz 的输入不做滤波（输入输出近似相等）。

### 3.2 **重点怀疑项：高采样率音频的 CPU 预算**

最近给高于 16 kHz 的输入加了加窗 sinc 低通（见 `src/audio.rs` 的 `Kernel`）：每个输出采样做约 `2 × ceil(2.75 × 源采样率 ÷ 2000)` 次乘加（48 kHz 约 132 次，384 kHz 封顶 1024 次）。而压缩格式（尤其是全静音的 FLAC）体积可以极小但解出很长的音频：25 MiB 的请求体上限（`ServerConfig::max_body_bytes`）下，**10 分钟 × 高采样率**的静音 FLAC 完全可能装得下。

请实测并回答：
1. 用程序生成静音 FLAC（可用 `flacenc` 之类的纯 Rust 编码器作为 dev-dependency，或手写最简的 FLAC 帧；也可用 `ffmpeg` 在开发期生成后以 base64 提交成小夹具），采样率分别为 48000、96000、192000、384000，时长 10 分钟，发起一次 `decode`，记录**发布构建（`--release`）下的耗时**和峰值内存。
2. 若 192 kHz 以下任一情形发布构建耗时超过 **5 秒**，或任意情形峰值内存超过 **200 MiB**，必须修复。允许的修复手段：(a) 在 `Resampler::new` 里对 `rate > 192000` 直接返回“不支持”；(b) 对内核半宽设更低的上限；(c) 使用更高效的多相分解；(d) 给解码加一个“工作量预算”（输入帧数 × 内核宽度）超限即返回 `TooLong`。选最小的改动，并保证 `tests/resample.rs` 里已有的质量断言（带外衰减 > 40 dB、带内幅度误差 ≤ 2%、无时间偏移）依然通过。
3. 把测得的耗时/内存表写进 `libs/voice-service/README.md` 的“已知限制”。

### 3.3 HTTP 层

起一个用假后端的服务（`tests/common/mod.rs` 里有假实现，可复用），然后：
- 对 `/v1/audio/transcriptions` 发随机的 multipart（合法 boundary 加随机体、重复字段、缺少 `file`、超长字段名、嵌套/畸形头部、截断的 body、chunked 与 `Content-Length` 不一致）；对 `/v1/audio/speech` 发随机 JSON（深度嵌套、超大数字、非 UTF-8、重复键）；对 `/mcp` 发随机 JSON-RPC（缺字段、错类型、批量数组、巨大 id、深度嵌套的 `params`）。
- 要求：服务**不 panic**（用 `tokio` 的 panic 钩子或检查任务是否崩溃）、每个请求在 5 秒内得到响应、状态码在 4xx/5xx 的合理范围、响应体仍是约定的 JSON 错误格式、服务在这一轮之后仍能正常处理一个合法请求。
- 慢速攻击：慢速发送请求头/体（每秒几字节）不应长期占用资源（现有读体超时 30 秒；验证它真的生效，且同时存在多个慢连接时不会拖垮合法请求）。

## 4. 目标二：`libs/link-protocol`

对以下函数做属性/随机测试，要求**任何输入都不 panic**，且错误类型正确：
- `envelope::open`：随机的 `Envelope`（`ep`/`ct` 为随机字符串或随机 base64、`seq` 取 0 和 `u64::MAX`、`v` 取各种值、`from`/`to` 为空或超长）；
- `pairing::QrPayload::decode`：随机字符串、前缀 `xbl1:` 加随机 base64、合法 base64 的随机 JSON、字段类型错误、公钥/密钥长度不对；
- `replay::ReplayGuard::check`：随机序列（含乱序、重复、`ep` 的前 8 字节大小关系各种组合）——属性：**接受过的 `(启动计数, seq)` 不会再被接受；启动计数更小的永远被拒绝**；
- `envelope::unpad`、`pad`：任意字节往返；`pad` 的输出长度总是 256 的倍数且 ≥ 输入长度 + 1；
- `keys::DeviceKey::agree`：随机的 65 字节、首字节非 0x04、不在曲线上的点，不 panic。
`open` 对“篡改任意一个可见字段或密文任意一位”必须失败（属性测试，至少 1000 次随机）。

## 5. 目标三：`services/server-link` 的 WebSocket 帧

服务通过 WebSocket 接收文本帧 `{"op":"send","env":{…},"notify":bool}` 与 `{"op":"ping"}`。测试需要 Postgres（环境变量 `TEST_DATABASE_URL`，没有则跳过并在交付说明里写明），复用 `server_link::testing::TestServer` 起真实服务（见该库 `src/testing.rs` 和 `src/tests.rs` 的写法）。

**重点怀疑项**：服务端的 WebSocket 升级没有设置 `max_message_size`/`max_frame_size`，而库默认值很大（单消息可达数十 MiB），一个已登录设备可以发一个巨大的文本帧，在服务端解析之前就占满内存。请：
1. 先写测试证明（发一个例如 32 MiB 的文本帧，观察服务端是否接受并分配）；
2. 修复：升级时设置合理上限（信封密文最大 256 KiB，加上 JSON 开销，单消息上限取 512 KiB 即可），超限应断开连接而不是继续读；
3. 加回归测试：超限帧断开连接，随后其他设备/连接不受影响。

其余测试：随机文本帧（非 JSON、深度嵌套 JSON、巨大数字、`op` 未知、缺字段、字段类型错）、二进制帧、连续快速发送、半开连接；要求：服务不 panic、该连接按约定收到 `error` 帧或被关闭、**其他连接不受影响**、服务的内存没有随这些帧持续增长（粗略检查：循环发送后进程的 RSS 增长小于一个合理的值，或用计数分配器）。
