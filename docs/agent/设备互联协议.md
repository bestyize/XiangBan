# 设备互联协议 v1

状态：L0 规范稿（2026-10-28）。对应 [实施计划_手机桌面互联](../product/实施计划_手机桌面互联.md)。参考实现与测试向量在 [`libs/link-protocol`](../../libs/link-protocol/README.md)；**桌面端（Rust）与手机端（Kotlin）都必须通过 `vectors/v1.json`**。向量已用一份独立的 Python 实现交叉验证过（只用标准密码学库，不依赖我们的 Rust 代码），说明规范本身可以被不同语言照着实现。

## 1. 角色与原则

| 角色 | 说明 |
| --- | --- |
| 桌面（desktop） | 电脑上的小伴。会话、记忆、权限的唯一来源，也是执行者 |
| 手机（phone） | Android 小伴。遥控桌面，不保存桌面的历史（只缓存） |
| 中转（server-link） | 独立服务。只认账号、记配对关系、转发加密信封、报在线状态。**看不到正文** |

1. 两层认证：**账号**（统一账号中心令牌，中转用）+ **设备密钥**（配对时建立，端到端用）。
2. 中转不存消息历史；唯一的暂存是通知类信封（§5.3），有数量和时间上限。
3. 手机发来的指令视为“远程来源”，由桌面按最严格权限处理（桌面侧策略，不在本协议里）。
4. 任何未知字段、未知消息类型一律忽略（回 `unsupported`），保证新旧版本互不崩溃。

## 2. 密码学

| 用途 | 算法 |
| --- | --- |
| 设备密钥对 | **ECDH P-256**。私钥 32 字节；公钥 SEC1 未压缩格式 65 字节（首字节 `0x04`） |
| 共享秘密 | ECDH 结果的 x 坐标，32 字节 |
| 密钥派生 | HKDF-SHA256 |
| 加密 | **AES-256-GCM**，12 字节随机数，16 字节标签 |
| 配对证明 | HMAC-SHA256 |
| 编码 | 二进制字段在 JSON 里一律 base64url（无填充）；向量文件里的 `*_hex` 是小写十六进制 |

选 P-256 与 AES-GCM 是因为 Android（minSdk 24）、JVM、iOS、Rust 都有原生或成熟实现，手机端不用额外引入加密库；私钥可放在 Android Keystore。

### 2.1 配对密钥 PRK

```
shared = ECDH(自己私钥, 对方公钥)                     // 32 字节
PRK    = HKDF-Extract(salt = 一次性密钥 s, ikm = shared)  // = HMAC-SHA256(key = s, data = shared)
```

两端各自算出同一个 PRK，长期保存（手机在 Keystore，电脑在系统钥匙串）。一次性密钥 `s` 配对后可丢弃。

### 2.2 消息密钥（每个方向、每个会话各一把）

```
PRK_e = HKDF-Extract(salt = ep, ikm = PRK)
K     = HKDF-Expand(PRK_e, info = "xb-link/1 key " + from + ">" + to, 32)
```

`from`、`to` 是设备编号的 UTF-8 字节。方向不同密钥不同。

### 2.3 会话标识 `ep` 与序号

- `ep` 共 16 字节：**前 8 字节是发送方持久化的启动计数**（大端，每次启动加一后先落盘再使用），后 8 字节随机。
- 每个 `ep` 下序号 `seq` 从 0 开始，每发一条加一。
- 随机数 `nonce` = 4 字节 0 + `seq`（8 字节大端）。因为每个 `ep` 对应不同的密钥，随机数不会在同一把密钥下重复。
- 计数没落盘就重启也不会发生随机数重用（随机部分不同 → 密钥不同），只是接收端会因“计数相同、`ep` 不同”拒绝，提示需要重新配对（见 §6）。

### 2.4 信封

```json
{ "v": 1, "from": "dsk_…", "to": "phn_…", "ep": "<base64url 16B>", "seq": 12, "ct": "<base64url>" }
```

- 明文先做 ISO/IEC 7816-4 补齐（末尾加 `0x80`，再补 `0x00` 到 **256 字节的整数倍**），再加密，以隐藏真实长度。
- 认证附加数据 AAD = `"xb-link/1" 0x00 from 0x00 to 0x00 ep(16B) seq(8B 大端)`。
- 单个信封的 `ct`（含标签）不超过 **256 KiB**。
- 接收方只接受 `from`/`to` 与自己认定的配对双方一致的信封。

### 2.5 接收端重放防护

对每个配对对端维护 `(启动计数, ep, 最大序号)`，**必须持久化**：

| 情况 | 处理 |
| --- | --- |
| 启动计数比当前大 | 对方重启了：切到新会话，序号重新开始 |
| 启动计数相同 | 必须是同一个 `ep`，且 `seq` 大于已收到的；否则拒绝 |
| 启动计数更小 | 旧会话，拒绝 |

只在**解密成功之后**更新状态；允许序号跳号（离线时会丢消息），不允许回头或重复。

## 3. 配对

```
桌面                                  中转                                 手机
 │ 生成设备密钥对（私钥进钥匙串）                                              │
 │ POST /devices，POST /pair-codes ────►│ 记设备、发一次性配对码（5 分钟）         │
 │ 显示二维码 xbl1:<base64url(JSON)>                                         │
 │                                      │                       用同一账号登录、扫码
 │                                      │◄──── POST /pair {code, 手机公钥, proof}
 │◄── pair.request {手机公钥, proof} ───│
 │ 校验 proof；通过则 confirm ─────────►│ 激活配对 ───── pair.confirmed ─────►│
 │ PRK = 派生(…)                         │                         PRK = 派生(…)
```

**二维码内容**（文本 `xbl1:` + JSON 的 base64url）：

```json
{ "r": "wss://link.…", "d": "<桌面设备编号>", "c": "<一次性配对码>", "k": "<桌面公钥 base64url>", "s": "<一次性密钥 32B base64url>" }
```

二维码走带外（摄像头），中转看不到 `k` 和 `s`。

**手机的证明**：`proof = HMAC-SHA256(key = s, "xb-link/1 pair-proof" 0x00 phone_id 0x00 desktop_id 0x00 phone_pub(65B))`。桌面验证通过才认这个手机公钥；**中转不知道 `s`，因此无法冒充手机，也无法把自己的公钥塞进配对**。这一步用户无感，不需要核对任何数字。

**手机还要核对**：中转返回的桌面公钥必须与二维码里的 `k` 一致，否则放弃。

**窗口与限制**：配对码 5 分钟有效、一次性；一个码最多被兑换 5 次（被桌面拒绝的也算），超过即作废；兑换按账号限频；桌面只在用户点了“连接手机”的窗口内接受 `pair.request`；同一账号下才能配对（中转校验）；配对成功后桌面立即作废二维码。

**撤销**：任一端“移除设备”→ 通过已加密通道发 `unpair`（若对端在线）并调用中转撤销；本端删除 PRK 和重放状态。丢了手机：在电脑端移除，或在账号中心“退出所有设备”（令牌失效，中转拒绝连接）。

## 4. 中转接口（server-link，L1 实现）

认证：`Authorization: Bearer <账号访问令牌>`，服务离线验签（与 server-ai 同一套 JWKS 方式）。浏览器/部分客户端设不了请求头时，WebSocket 可把令牌放在子协议里：`["xb-link", "xiaoban-token.<令牌>"]`。

| 接口 | 说明 |
| --- | --- |
| `POST /api/link/devices` | `{kind: "desktop"\|"phone", name, public_key}` → `{device_id}`；同一账号同一公钥幂等 |
| `GET /api/link/devices` | 自己名下的设备与在线状态 |
| `DELETE /api/link/devices/{id}` | 撤销设备及其所有配对，并断开连接 |
| `POST /api/link/pair-codes` | 桌面申请：`{device_id}` → `{code, expires_at}` |
| `POST /api/link/pair` | 手机兑换：`{code, device_id, proof}` → `202 {pairing_id, desktop: {id, public_key}}`，同时向桌面推 `pair.request` |
| `POST /api/link/pairings/{id}/confirm` | 桌面确认（已验证 proof）；中转向手机推 `pair.confirmed` |
| `POST /api/link/pairings/{id}/reject` | 桌面拒绝 |
| `GET /api/link/pairings` | 已激活的配对 |
| `DELETE /api/link/pairings/{id}` | 解除配对 |
| `GET /api/link/ws?device_id=…` | WebSocket，见下 |

另：`GET /api/link/pairings?device_id=&status=active|pending` 列出配对；桌面取 `pending` 时每项带手机的 `proof`（桌面不在线时错过 `pair.request` 可以靠它补）。

错误统一 `{ "code": "…", "message": "…" }`：`unauthorized`、`forbidden`、`not_found`、`code_expired`、`code_used`、`too_many_attempts`、`rate_limited`、`payload_too_large`、`device_revoked`。

### 4.1 WebSocket 帧（文本，JSON）

服务端 → 设备：

| `op` | 内容 |
| --- | --- |
| `ready` | `{device_id, server_time}` 连接成功 |
| `presence` | `{device, online}` 已配对的对端上线/下线；刚连上时按当前状态补发 |
| `pair.request` / `pair.confirmed` / `pair.rejected` | 配对过程通知 |
| `deliver` | `{env: <信封>}` 对端发来的信封 |
| `undelivered` | `{to, seq, reason: "offline"}` 你发的信封没送达 |
| `unpaired` | `{device}` 对端或你已被解除配对 |
| `error` | `{code}`，如 `rate_limited`、`payload_too_large`，严重的随后断开 |

设备 → 服务端：

| `op` | 内容 |
| --- | --- |
| `send` | `{env: <信封>, notify?: true}` 转发给 `env.to`（必须是已配对的设备） |
| `ping` | 保活；服务端回 `pong`。空闲 25 秒发一次 |

中转只校验：`env.from` 等于连接的设备、`env.to` 已配对、信封大小。**不解析也无法解析 `ct`。**

### 4.2 暂存与限流

- 对端离线时，只有 `notify: true` 的信封会暂存，每个对端最多 50 条、24 小时过期；对端上线后按序补发。其他信封直接回 `undelivered`。**指令类消息不要加 `notify`**，避免电脑上线后执行过时的指令。
- 限流（可配置，初值）：每设备 30 条/秒、1 MiB/秒；配对码尝试每账号每分钟 10 次。
- 中转的日志和数据库不记录 `ct`，只记设备编号、大小、时间、结果。

## 5. 应用消息（加密后的明文）

UTF-8 JSON 对象，公共字段：`t`（类型）、`id`（发送方生成的消息编号，用于幂等和回执）。

| `t` | 方向 | 字段（要点） | 说明 |
| --- | --- | --- | --- |
| `hello` | 双向 | `v`（协议版本）、`caps`（能力列表）、`app`（应用版本） | 连接后各发一次；协商取共同能力 |
| `sessions.list` | 手机→桌面 | `limit`、`cursor?` | 请求会话列表 |
| `sessions.page` | 桌面→手机 | `items:[{id,title,updated_at,state}]`、`cursor?` | 回应 |
| `sessions.changed` | 桌面→手机 | `items`（增量） | 列表变化 |
| `session.open` | 手机→桌面 | `session`、`after?`（已有的最后一条消息编号） | 打开会话并订阅事件 |
| `session.snapshot` | 桌面→手机 | `session`、`messages`（分页）、`state`、`cursor?` | 当前内容 |
| `session.close` | 手机→桌面 | `session` | 取消订阅 |
| `message.send` | 手机→桌面 | `session?`（空则新建）、`text`、`client_id` | `client_id` 用于幂等；桌面回 `message.accepted` |
| `message.accepted` | 桌面→手机 | `client_id`、`session`、`message_id` | 已写入队列 |
| `event` | 桌面→手机 | `session`、`kind`（`text.delta`/`tool.start`/`tool.end`/`state`/`turn.done`/`error`）、`data` | 流式回复与进度 |
| `approval.request` | 桌面→手机 | `approval_id`、`session`、`title`、`detail`、`risk`（`low`/`high`）、`options` | 待确认 |
| `approval.decision` | 手机→桌面 | `approval_id`、`choice` | 手机的决定；`risk=high` 时手机需二次确认 |
| `approval.resolved` | 桌面→手机 | `approval_id`、`by`（`desktop`/`phone`/`timeout`） | 任一端处理后广播 |
| `unpair` | 双向 | 无 | 通知对方解除配对 |
| `unsupported` | 双向 | `ref`（对应消息编号）、`t` | 不认识的类型 |

约定：
- `text.delta` 之类流式事件无需回执；丢失靠 `session.open` 带 `after` 重新对齐。
- 所有“手机→桌面”的写操作带 `client_id` 或 `approval_id`，桌面据此幂等。
- 应用层心跳不需要（WebSocket 层已有 `ping`）；延迟可用 `hello` 往返估计。

## 6. 异常与恢复

| 情况 | 处理 |
| --- | --- |
| 连接断开 | 指数退避重连（1、2、4…最多 30 秒，加抖动）；重连后重新 `hello`，手机对打开的会话重发 `session.open{after}` |
| 对端重启 | 新的 `ep`（计数更大），接收端自动切换 |
| 接收端报“计数相同、ep 不同” | 对端没能持久化启动计数：提示“需要重新配对”，不要自动放行 |
| 解密失败 | 丢弃该信封，不回应，计数；连续多次失败时提示可能被篡改或需要重新配对 |
| 协议版本不匹配 | `hello` 里 `v` 不兼容时，两端各自提示升级，不继续 |
| 电脑休眠/离线 | 手机收到 `presence{online:false}`，隐藏遥控入口，输入框切回云端小伴 |

## 7. 威胁模型

| 威胁 | 结论 |
| --- | --- |
| 中转被动窥探（诚实但好奇） | 只能看到设备编号、时间、信封大小（已按 256 字节补齐）。正文不可见 |
| 中转被入侵后主动攻击 | **不能伪造或篡改消息**（AEAD）；**不能冒充手机**（缺 `s`）；**不能重放**（接收端重放防护）；能丢弃、延迟、断连（可用性问题，不是保密性问题） |
| 账号令牌被盗 | 攻击者能注册设备、申请配对，但没有二维码里的 `s`，proof 通不过，桌面拒绝。拿不到已有配对的 PRK，看不到内容 |
| 二维码被拍到 | 5 分钟内有效且一次性；被别人先扫会让真正的手机配对失败，用户会看到失败，重新生成即可 |
| 手机丢失 | 在电脑端移除设备，或账号中心退出所有设备。PRK 在 Keystore，不可导出；可选要求锁屏验证 |
| 电脑被入侵 | 攻击者本来就能操作小伴，不在本协议防护范围；PRK 在系统钥匙串，与账号密码同等对待 |
| 流量分析 | 长度已粗粒度隐藏；时间和频率仍可见 |
| 拒绝服务 | 中转限流；单信封 256 KiB 上限；配对码兑换次数上限 |
| 账号令牌被盗后占用设备连接 | 持令牌者可用设备编号连上来顶掉真连接，造成骚扰；仍看不到、伪造不了内容（AEAD）。彻底解决需要设备对连接做签名挑战，列入 v2 |
| **没有前向保密（已知限制）** | 设备密钥泄露后，此前被截获的密文可以解开。v2 计划在每个 `ep` 增加临时 ECDH（用 PRK 做认证），本版不做 |

## 8. 版本与扩展

- 信封 `v`、`hello.v`、`caps` 三处版本信息；新增消息类型靠 `caps` 协商，不改信封。
- 破坏性变更（算法、编码）升 `v`，两端同时支持旧版至少一个发布周期。
- iOS 暂不做；算法选择已保证 iOS 将来可直接实现（CryptoKit 原生支持 P-256、AES-GCM、HKDF）。
