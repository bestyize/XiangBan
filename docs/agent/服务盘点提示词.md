# 服务盘点提示词（只读）

目的：弄清楚线上到底有哪些服务、各自在哪台机器、什么版本、占什么端口、数据库在哪。**整个过程只读，不改任何东西**，所以可以放心交给 AI。盘点结果是后面部署（见 [手机互联整体部署提示词](手机互联整体部署提示词.md)）的前提。

交给 AI 之前，你准备好：每台服务器的 SSH 登录方式（至少香港机；如果有独立的资源机、其他机器也一并给）。没有的机器就说没有，不要让 AI 猜。

## 提示词

```text
你是一名运维工程师。任务：对“小伴”项目的线上服务器做一次只读盘点，产出一张清单。仓库是 bestyize/XiangBan（main 分支）。

硬性约束（先读完再动手）：
1. 全程只读。禁止：重启或停止任何服务/容器、修改任何文件（含 Nginx、.env、systemd 单元）、执行 docker compose up/down/pull/build、删除或清理任何东西、运行数据库写语句、安装软件。只允许查看类命令（例如 docker ps/inspect/logs --tail、systemctl status/cat、ss -ltnp、nginx -T、ls -l、stat、cat 非敏感文件、df -h、free -h、curl 访问健康检查与只读接口）。拿不准一条命令会不会改东西，就不要执行，写进“未能核实”里。
2. 密钥不外泄。读 .env、systemd 环境文件、compose 文件时，只记录“有哪些变量名、值是否为空/是否看起来是默认值”，**绝不把密码、令牌、密钥、连接串里的密码写进报告或聊天记录**；贴命令输出前先打码。
3. 不确定就写“未知”，不要猜。每个结论后面写依据（用了哪条命令、看到什么）。

已知线索（仅供你定位，以实际为准）：
- 账号中心 server-account：独立 compose 栈，常见目录 /home/ubuntu/xiangban-account，端口 55009，域名 account.xiangban.xyz，镜像名 xiangban-account:<标签>，自带 PostgreSQL。
- 论坛 server-forum：香港机 /home/ubuntu/xiangban-forum，systemd 服务 server-forum，监听 127.0.0.1:55010，域名 chat.xiangban.xyz，库 xiaban_forum 在 wallpaper_postgres 容器里（角色 forum）；README 写的上次部署是 2026-10-11。
- 资源机 server-resource：独立的大带宽机器，签名下载内容包与封面图，健康检查 GET /health。
- 壁纸站 server-xiangban-wallpaper：wallpaper.xiangban.xyz。
- 小伴市场 server-xiaoban-market：独立 compose 栈（infra/market）。
- 原 xiaban-api 已移除；若机器上仍有旧容器或数据，仅记录现状，不做清理。
- AI 网关 server-ai（域名可能是 ai.xiangban.xyz，请核实线上是否部署）及其上游 New API（infra/new-api，默认回环 :3000）。
- 互联中转 server-link：新服务，预期端口 55030、域名 link.xiangban.xyz，可能尚未部署。
- 注意 server-ai、server-forum、server-market 的默认端口都是 55010，同一台机器上不能同时用。

对每台机器依次做：
A. 机器概况：主机名、公网/内网 IP（可打码一部分）、系统版本、CPU/内存/磁盘使用（df -h、free -h）、uptime。
B. 在跑的东西：docker ps -a（容器名、镜像:标签、状态、端口映射）、docker images 里与小伴相关的镜像和标签、docker compose ls、systemctl list-units --type=service --state=running 里与小伴相关的服务、ss -ltnp 的全部监听端口及对应进程。
C. Nginx：nginx -T 的结果，整理成“域名 → 证书是否存在及到期时间 → 反代到哪个上游端口”的表；指出哪些域名指向了不存在或没监听的上游，以及 limit_req_status 等是否有重复定义（nginx -t 的结果也记录）。
D. 每个服务各给出一行：所在目录、部署方式（compose / systemd / 其他）、版本依据（镜像标签、二进制修改时间、git 提交号或版本号，能拿到哪个写哪个）、对应的 .env 或环境文件路径与权限（只写路径和权限，不写内容）、数据库在哪个容器/实例、数据卷名、有无备份任务及最近一次备份时间。
E. 只读的健康与版本探测（从服务器本机和公网域名各试一次，写下 HTTP 状态码）：
   - 账号中心：GET /api/health；POST /api/auth/password/login，body {"identifier":"nobody-check","password":"x","client_id":"xiaoban-android"}：返回 401 说明已登记 xiaoban-android 客户端，返回 400 说明没登记（这是一次错误登录尝试，只做一次，不要重复）。
   - 论坛：GET /api/packs、/api/weekly、/api/projects、/api/topics?sort=latest，以及不带令牌的 /api/me/notifications/unread：新版本前四个返回 200、最后一个 401；返回 404（body 含“接口不存在”）说明线上是缺少内容层的旧版本。同时看启动日志里有没有 extra_clients 字样（docker logs / journalctl 各取最后几十行，注意打码）。
   - 资源机：GET /health。 AI 网关：GET /api/health。 互联中转：GET /api/link/health，以及不带令牌 GET /api/link/devices（预期 401）。
   - 其他服务：各自 README 里写的健康检查，没有就只看端口是否在监听。
F. 风险观察：磁盘或内存紧张、证书 30 天内到期、容器反复重启、日志里的持续报错（只摘要）、对公网开放了不该开放的端口（例如数据库 5432、各服务端口直接监听 0.0.0.0 而不是 127.0.0.1）、.env 权限过宽、没有备份。

交付（一份报告，Markdown）：
1. 机器清单表。
2. 服务清单表：服务 | 机器 | 域名 | 端口 | 部署方式 | 版本依据 | 健康状态 | 数据库位置 | 备份。线上不存在的服务也要列一行，写“未部署”。
3. 域名/Nginx 表。
4. 端口占用表，并指出冲突或隐患。
5. 风险观察与建议（只建议，不执行）。
6. “未能核实”清单：每一项写明为什么没核实（权限不够、命令可能改东西、需要令牌等）。

最后一句话回答三个问题：线上的论坛是不是缺少内容层的旧版本？账号中心有没有登记 xiaoban-android？AI 网关（ai.xiangban.xyz）线上到底有没有？
```
