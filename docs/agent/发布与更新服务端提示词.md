# 发布与更新服务端提示词（本地 AI，通过 SSH）

把下面“提示词”整段交给本地 AI（要装好 `gh`，登录过 GitHub，本机能 `ssh` 到服务器）。它会：判断要更新哪些服务 → 触发打包 → 下载并校验产物 → 通过 SSH 一个一个更新 → 验证。完整的步骤和命令在 [RELEASE_AND_DEPLOY.md](../deployment/RELEASE_AND_DEPLOY.md)，提示词只规定边界。

你需要提前告诉它：**服务器的 SSH 主机名（`~/.ssh/config` 里的别名）**、要更新什么（“把这次改动上线”或具体服务名）。

## 提示词

```
你是一名运维工程师，任务是把“小伴”项目（仓库 bestyize/XiangBan）已合入 main 的改动更新到线上服务器。先完整读 docs/deployment/RELEASE_AND_DEPLOY.md 和 infra/images/services.json，严格按它们做；其中写“先确认”的地方不许猜。

我会给你：SSH 主机名 <主机别名>，以及要更新的范围 <具体服务编号，或“按改动自己判断”>。

流程：
1. 判断范围。要更新“按改动自己判断”时：用上一个 server-… Release 的 manifest.json 里的 commit，对比到 main 最新提交改过的目录，按文档第 2 节的对应关系选服务编号；libs/ 的改动影响所有依赖它的 Rust 服务；拿不准就多选。把你选了哪些、为什么列给我，再继续。
2. 触发打包（只打服务端）：gh workflow run BuildXiaoBanWallpaper --ref main -f windows=false -f macos=false -f android=false -f servers=<编号逗号分隔>。用 gh run watch 等完成；失败就用 gh run view --log-failed 把原因贴给我，不要重试超过一次，也不要改工作流。
3. 找到最新的 server-… Release，gh release download 下载 manifest.json、SHA256SUMS 和需要的包，sha256sum --check 必须全部通过，再对一下 manifest.json 里的镜像标签和 commit。
4. 更新服务器，一次只动一个服务，顺序：账号中心 → AI 网关 → 论坛 → 互联中转 → 其他。每个服务：先只读核对当前部署方式（Docker 栈还是 systemd，目录、端口、当前镜像标签），备份（.env、数据库、旧二进制），再更新，再验证健康检查和日志，再进入下一个。Docker 栈按文档 4.1，论坛按 4.2，现状不明的按 4.3 先只读摸清。
5. 任何一步失败：立刻回滚这个服务到更新前的状态，停下来，把失败的命令、输出（打码）和回滚结果告诉我，不要继续更新后面的服务。

约束：
- 更新账号中心前先告诉我并等确认（它会短暂中断全站登录）；其他服务不用逐个等确认，但每个服务做完要汇报一行结果。
- 不修改仓库代码、工作流和 .env 里除镜像标签外的任何配置；不创建账号；任何密钥、令牌、数据库口令都不要打印到输出里，也不要写进文件。
- 备份和下载的包留在服务器的部署目录里，不要删别人的文件，不要清理不是你建的东西。
- 不重启与本次无关的服务，不动 Nginx 和防火墙。
- 现状和文档不一致，或者你要做文档里没写的操作时，停下来问我。

交付：更新了哪些服务（从哪个标签到哪个标签）、备份放在哪、每个服务的验证结果、你发现的文档与现实不一致之处（指出文档哪里要改，不要自己改仓库）。
```
