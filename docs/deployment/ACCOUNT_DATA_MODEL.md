# 数字 ID 与功能数据

账号的稳定身份是 `users.id`（数据库生成的数字 ID）。邮箱用于验证和找回；昵称是可修改的展示信息，不作为功能表的关联键。

| 表 | 保存内容 | 用户关联 |
| --- | --- | --- |
| `users` | 账号创建、邮箱验证及基本设置 | `id` 主键 |
| `user_profiles` | 昵称与归一化后的唯一键 | `user_id` 主键／外键 |
| `user_avatars` | 不超过 65,536 字节的 JPEG 头像及随机资源键 | `user_id` 主键／外键 |
| `companions` | 小伴名字、性格 | `user_id` 主键／外键 |
| `checkins` | 每个下班日的打卡与回复 | `user_id` 外键 |
| `game_sessions` | 对局、成绩、消行数、最大方块及时间 | `user_id` 外键 |
| `afterwork_choices` | 每天下班后的安排 | `(user_id, work_day)` 主键 |
| `afterwork_preferences` | 常做安排与提示状态 | `user_id` 主键／外键 |
| `memories`、`unlocks`、`guardians` | 各自功能记录 | `user_id` 外键 |

## 登录状态

会话 API 返回 `profile.userId`、`profile.accountType`、`profile.avatarUrl`。有效的邮箱登录会话返回 `registered`，未登录访问返回 `guest`。

游客模式下，资料与体验记录（打卡、小伴档案、下班安排、游戏成绩等）仅保存在当前浏览器，不持久化到数据库中；退出登录或浏览网站绝不会新增数据库账号。页面明确提示：“游客数据仅保存在当前浏览器；清除浏览器数据、使用无痕模式或换设备后无法找回。创建账号后可保存并跨设备使用。”

新邮箱注册时必须提交用户名，用户名存为账号昵称并沿用统一长度与唯一性规则。登录页提供“已有账号登录”和“新用户注册”两个入口。邮箱验证码验证成功并确认唯一用户名后，才正式在数据库事务中创建账号与数字 ID。已有邮箱登录会保留原账号用户名与历史数据。

没有有效登录令牌时，已验证账号不会仅凭浏览器设备标识自动恢复。退出、过期或账号删除后会重新进入游客模式。客户端会在重新打开页面或窗口获得焦点时检查会话；账号 ID 改变时重建功能界面，并阻止把旧账号的写操作自动重试到新账号。

## 昵称与头像

昵称至少 2 个字符；纯英文或英文加数字至少 4 个字符；不能为纯数字，最多 24 个字符。大小写、全角字符和多余空格会归一化用于判重；数据库唯一键处理并发冲突。游客可保留默认的 ID 展示名。迁移会保留合法且唯一的旧昵称，其他情况退回 ID 展示名；旧值仍保存在 `companions.nickname` 作为迁移快照，该列不再参与新功能。

头像先在浏览器中心裁剪并缩小为 JPEG，压缩后不超过 64KB。服务端再次校验字节数、图片格式和尺寸，避免只依赖前端。头像内容单独存表，不写入账号基础行。随机资源键会在替换图片后更新，访问头像不需要把用户令牌传给图片地址。

## 功能扩展

未来功能应建立自己的表、服务和 API，以 `user_id` 外键关联 `users.id`。写入时从服务端认证主体获取 ID，不能信任客户端提交的用户 ID。不要把成绩、打卡历史或整块功能 JSON 塞入账号表。

新增功能同时应考虑账号合并、导出与删除。现有游戏和安排记录已接入这些流程；数据库外键负责级联删除。绑定已有邮箱并选择合并时，数据迁移到原邮箱账号的数字 ID，其昵称、头像和设置以原账号为准。

小游戏包通过已有的 nonce／消息来源校验向宿主页发送 `game.start`、`game.progress`、`game.result`，宿主页负责写入数据库，游戏 iframe 不持有用户令牌。目前保存的是对局与成绩指标，棋盘临时状态仍由当前游戏运行时管理。

旧版浏览器内的下班安排不会自动归入另一个账号。“我的”提供明确的导入按钮，并显示目标数字 ID；导入成功后再清除旧本机副本，同一天已有的云端安排优先保留。

验证码为 6 位、10 分钟有效、仅使用一次。发送邮件同时提供 HTML 和纯文本版本；HTML 使用小伴信件样式并突出显示可复制的验证码。
