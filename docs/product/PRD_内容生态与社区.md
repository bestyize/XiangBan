## 1. 背景与问题

### 1.1 已有的基础

| 能力 | 现状 | 来源 |
| --- | --- | --- |
| 资源包 | 桌面端可把自创的动态壁纸、桌面特效、桌面组件、小游戏导出为 zip，也能导入；导入只放进对应位置，不自动应用 | 桌面 README、`resource-pack-format.md` |
| 分享到论坛 | 各页有“分享到论坛”，聊天里的 `community_share` 工具可代办；论坛“小伴壁纸”“小伴游戏”板块对所有人开放发帖 | 桌面 README、论坛 README |
| 深链 | `xiaoban://market/...` 已注册，只唤起确认窗口，从不静默安装；真机未验证 | 市场 README |
| 目录与采集 | 市场服务有采集工作台、暂存区、审核入库，已对接 SkillHub，魔搭待配置 | 市场 README |
| 论坛 | 2026-10-11 部署；信任等级、积分、悬赏、附件、SEO 页面、站方批量发帖工具链（编辑令牌、待发布稿、`forum-post-studio` 技能） | 论坛 README |
| 手机方向 | 路线图已把“手机 App：电脑上小伴的遥控器和收集口”排在第 2 位，经 server-ai 中转 | `assistant-roadmap.md` |

### 1.2 缺口

1. **分享是单向的。** 作者导出 zip、手动传到论坛；浏览者只能下载附件，再自己去桌面端导入。看到好东西到用上它，中间隔着五六步。
2. **内容没有结构。** 论坛帖是文本加附件，没有“类型、预览、版本、校验值、被应用次数”，无法排行、筛选或审核。
3. **用户的沉淀都在本机。** 桌面端本地优先，换电脑或重装即丢失；没有云端的东西，就没有“我的作品”“我的方案”，社区里也没有身份可言。
4. **社区还不存在。** 论坛已部署但尚无用户；没有固定栏目，也没有种子内容。
5. **没有数据。** 商业企划里“当前日活与次日留存”至今是待确认；没有埋点，任何关于拉新和留存的判断都只是假设。
6. **UGC 合规项没补齐。** 论坛 README 的“二期未做”里有站内通知、屏蔽用户、敏感词；这些是手机 App 上架 UGC 类应用的前置条件。

### 1.3 外部参照

Wallpaper Engine 的创意工坊证明这类内容有真实需求，也暴露了开放社区的代价：不良内容、低质量上传，以及有报道称攻击者利用工坊投放恶意文件。结论是**“一键使用”的内容必须分级放行**，不能让任意用户上传的可执行内容直接跑在别人电脑上（见 §7）。

### 1.4 已确认的前提

| 前提 | 对本 PRD 的影响 |
| --- | --- |
| 团队 2–3 人，主要工作由 AI 完成 | 所有流程按“AI 起草、人终审”设计；审核与发布是单点瓶颈，每期产出量以一个人能审完为上限；不设需要随时响应的机制 |
| 论坛还没有用户，没有任何基线 | 前期内容必须由官方供给；开放用户发布、求助、挑战要等有访问信号后再做；第一阶段验证“能否带来访问”，不是“能否带来互动” |
| 产品以后会改名，但**现阶段沿用“小伴”**，改名不阻塞进度 | 见 §2.4：按“将来能低成本改名”的方式做 |
| 云端数据放自己的服务器，之后换大容量机型 | 见 §6.6 |
| 生成式内容合规暂不处理，规模变大后再说 | 记为已接受风险，见 §7 |
| 积分机制先不外露 | 界面不出现积分与悬赏金额，见 §6.5 |

## 2. 定位与目标

### 2.1 定位

产品是**个人助手 Agent + 桌面装扮**两件事，社区是夹在两者之间的内容层：

- 生产力侧：Agent、技能、连接器、工作流、GitHub 项目研究。
- 装扮侧：壁纸、特效、组件、伙伴、游戏、桌面方案。
- 社区把两侧的内容放在同一个地方分享、讨论，并且**每条内容都有一个动作按钮**（试用、安装、应用、复刻）。

产品以后会改名，届时“小伴”降为可选的“伙伴”之一。**现阶段沿用“小伴”这个名字**，改名事项见 §2.4。

### 2.2 目标

| 编号 | 目标 | 衡量 |
| --- | --- | --- |
| G1 | 让社区内容能一键用上 | 内容→应用转化率（§8） |
| G2 | 让创作者的作品有地方发、能被用 | 创作者→发布转化率 |
| G3 | 社区每周有稳定的新内容 | 周刊连续发布周数 |
| G4 | 用户的作品和方案有云端身份 | 登录用户中有云端方案/作品的比例 |
| G5 | 能回答“拉新和留存到底来自哪” | 有 7 日留存基线与分模块使用数据 |

### 2.3 非目标

- 不做付费内容交易、创作者分成、打赏（后续单独立项）。
- 不开放用户上传的**可执行内容**（HTML/脚本类）直接一键应用，除非通过审核（§5.2）。
- 不做短视频托管；分享海报和封面图，视频流量留给外部平台。
- 不做个人微信接入（路线图已决定不做）。
- 不做泛 AI 绘画/闲聊社区的专门运营；论坛已有板块，不追加投入。
- 不在本文规定手机端的 Agent 能力范围，以路线图为准（§6.9）。

### 2.4 品牌与改名

**决定：现阶段沿用“小伴”，改名往后放，不阻塞任何阶段。**

为了将来改名成本低，现在按下面的做法开发，几乎不增加工作量：

- **品牌字串集中管理。** 产品名、站点名、栏目名、海报文案不散落在页面和模板里，统一放在配置或文案文件（论坛站点名已有 `/api/config`，沿用）。
- **新增的标识不带品牌词。** 社区路径、内容包 id、周刊 slug、深链命名空间用中性词（`community`、`weekly`、`pack`），不再新增 `xiaoban-*` 形式的命名。已有的 `xiaoban://`、`~/.xiaobanwallpaper`、`xiaoban-community` 保持不动。
- **海报和周刊模板参数化。** 品牌名、Logo、配色作为变量，不烧进图片；改名时重新出图即可。
- **正文少提品牌名。** AI 生成的解读和周刊点评避免反复写“小伴”，用“它”“桌面端”等指代，减少将来批量替换。
- **改名时再做**：用户可见文案、域名、海报；新增新名称的深链协议并保留 `xiaoban://` 兼容；数据目录不迁移；商标、域名、应用商店重名自查。
- **回看时机**：建议 M1 结束时回看一次。品牌认知积累越多，改名越贵，所以不宜无限期拖延；但它不是任何阶段的前置条件。

## 3. 用户

| 用户 | 要什么 | 在社区里的主要动作 |
| --- | --- | --- |
| 装扮党 | 好看的桌面，不想折腾 | 逛、复刻桌面方案、收藏 |
| 办公效率用户 | 少做重复事 | 看项目周刊、装技能、导入工作流 |
| 开发者 / AI 玩家 | 追新项目，试新工具 | 看热榜解读、讨论、分享自己的项目 |
| 创作者 | 做出东西被人用 | 用 AI 或手工做内容包、发布、看被应用次数 |
| 手机轻用户 | 碎片时间 | 刷社区、问答、玩游戏，把东西“发到电脑” |

## 4. 产品结构

```text
入口层（拉新）      壁纸站 · 内容包预览 · 热榜 SEO 页 · 周榜海报
日常层（留存）      关怀提醒 · 小组件 · 专注 · Agent 日常任务
沉淀层（深留存）    账号云端：桌面方案 · 作品备份 · 收藏
关系层（放大器）    社区：项目话题 · 装扮内容包 · 助手能力与任务模板 · 桌面方案 · 求助 · 挑战 · 创作者
```

各层的作用：入口层负责被看见；日常层给每天打开的理由；沉淀层让用户越用越离不开；关系层把前三层的内容变成可传播、可协作的东西。

社区的内容覆盖产品的两侧：装扮类（特效、壁纸、组件、游戏、方案）和助手能力类（例行、提醒、任务、目标、技能、专家）。两类混在同一个内容流里，用类型标签区分，不设分栏或切换（§4.2）；助手的工作能力要在社区里被看见、能被试用，不能只剩装扮。

### 4.1 栏目节奏

固定节奏让用户知道什么时候该来。受限于一个人终审，**M1 只做周一的热榜周刊**，其余栏目在有稳定内容来源后依次加入。初值如下。

| 日 | 栏目 | 内容 | 主要来源 |
| --- | --- | --- | --- |
| 周一 | 热榜周刊 | 本周值得看的开源项目与产品，10 条以内 | 采集 + 解读 + 人工终审（§6.1） |
| 周三 | 创作精选 | 本周被应用最多或编辑挑选的内容包 | 用户 + 编辑 |
| 周五 | 桌面方案 | 精选桌面方案，可复刻 | 用户 + 编辑 |
| 周末 | 主题挑战 | 官方出题，投稿与投票 | 用户 |

### 4.2 社区信息架构与界面

现有论坛是文字板块式，与“内容优先”的定位不匹配。论坛还没有用户，没有历史内容要迁移，现在是调整结构成本最低的时候。**保留后端能力，重做板块和前台界面。**

**社区栏目**（手机应用里在“社区”页顶部横排，网页上在导航栏）

| 入口 | 内容 | 呈现 |
| --- | --- | --- |
| 首页 | 内容包、桌面方案、能力卡、项目解读混排，不放周刊头图。顶部左边是品牌标识、右边是搜索图标，下面是二级 Tab（可横向滑动）：全部、周刊、特效、壁纸、组件、游戏、方案、例行、提醒、任务、目标、技能、专家，点哪个就只看哪类；不分组 | 卡片流：“全部”和视觉类（特效、壁纸、组件、游戏）是双列瀑布流；文字为主的能力类（例行、提醒、任务、目标、技能、专家）和桌面方案，筛选后改为单列，卡片更宽，才能读完说明和权限提示 |
| 资源 | 资源分享（保留，见下） | 列表加封面 |
| 讨论 | 求助（“我想要一个……”，可采纳回答）、闲聊、产品反馈、站务公告 | 文字列表（保留论坛形态但降权） |
| 我的 | 我的发布、收藏、桌面方案、消息、官方更新日志（手机应用里是底栏入口，网页上在头像菜单） | — |

**周刊是首页里的一个二级 Tab**（紧跟“全部”之后），不占首页头图，也不再是单独的一级栏目：点“周刊”后，下面的内容区换成本期榜单（期数与日期、往期入口、编号榜单；每条有编号、一句话说明、类型标签、风险提示、“试用 / 收藏”按钮和讨论数，见 §6.1），其余时候首页保持精简，信息流从屏幕最上方开始。

**取消与保留**

- **福利羊毛：取消。** 包括羊毛帖类型、`/deals` 页面、到期下架任务和相关分类；清理时同步改论坛 README 与 PRD_论坛。
- **资源分享：保留，规则不变**，仅限合法来源（正版、开源、免费软件；片单、影评、乐评、歌单；公版或授权影音；公开课程资料；自己的作品）。建议二级分类：精品软件、影音推荐（片单、影评、乐评、歌单）、学习资料。原来的“电影资源”“音乐资源”名称容易引来下载求助，改名与规则对齐。
- **按产品划分的板块**（小伴壁纸、小伴游戏、小伴App）不再保留：内容包归入首页内容流，官方更新日志放“我的”和首页头图。
- **游戏**是首页内容流里的一个类型，详情页提供“在线试玩”（§6.2）。升为独立入口的时机：游戏数量和游玩次数足以撑起一页时，手机端优先。

**界面方向**

- 以小红书式的卡片流为骨架，沿用手机壁纸 App 与桌面控制台已有的红色主色（#FF2442）和白底，三端风格一致。
- 周刊页参考 Product Hunt：编号榜单，每条一句话，加类型标签和讨论数。
- 内容包详情页参考创意工坊：大预览图，一个醒目的“应用到我的桌面”按钮（游戏为“在线试玩”），下方是版本、大小、权限、信任级别和评论。
- 手机应用的底栏沿用壁纸 App 已有的悬浮胶囊样式：白色圆角带阴影，选中项展开成红色胶囊带文字，其余只留图标。白字按钮的红色从 #FF2442 略加深到 #E3203C，以保证文字对比度。
- 能力详情页把“完整提示词”“能做 / 不能做”“运行位置”“安全说明”放在显眼位置，让用户在订阅前看得到；装扮详情页用通栏预览图，并显示“权限与安全”。
- **视觉规则（小红书式克制）**：除品牌红外只用黑、灰、白；红色只用于选中态、主按钮和少量强调小字（如悬赏积分、已采纳）。标签和状态一律是浅灰小字，不做彩色药丸。内容流以图为主，卡片只有标题（两行）、作者和点赞/使用数；列表页（资源、讨论、回答）整块白底，条目之间只有 0.5px 细线，不用一条一个圆角卡。字号只用 15（标题）、13（说明）、12（元信息）三档为主，正文色 #222，次要 #666，元信息 #999。封面用渐变加柔光，不用平涂色块。
- 社区页顶部只有一行：左边是品牌标识（图标加“小伴”），中间是一级栏目（首页 / 资源 / 讨论），右边是一个搜索图标（点开进入搜索页，不放整条搜索框）。品牌标识待改名后统一替换（§2.4）。
- **社区页分两层 Tab**：一级栏目（首页 / 资源 / 讨论）与品牌标识、搜索图标同在顶部一行，居中，字号大、红色下划线；二级 Tab 紧贴其下一行，左对齐、可横向滑动，字号小一号，选中项加粗并带一小段红色下划线。首页和作品页的二级 Tab 是类型（全部、特效、壁纸、组件、游戏、方案、例行、提醒、任务、目标、技能、专家），资源是（全部 / 精品软件 / 影音推荐 / 学习资料），讨论是（全部 / 求助悬赏 / 闲聊 / 产品反馈 / 公告）。游戏页和“我的作品”页也用同样的 Tab（来源或状态，带数量）。胶囊标签只留给发帖时的分类选择这类表单场景。
- 不做推荐算法，排序只有最新、热门、本周三种。
- 项目解读没有预览图，用参数化模板自动生成封面，与周刊海报共用一套模板。

**分期**

- M0：信息架构定稿并出可点击原型。原型已出 19 页，覆盖社区首页（含周刊 Tab）、资源 / 讨论、帖子详情、搜索、装扮详情、能力详情、桌面方案详情、游戏与试玩、我的、我的作品、设置、发布作品、发帖、小伴AI 首页和对话页；未画“我的电脑”配对页、收藏与消息。
- M1：前台改版第一版——首页（含周刊 Tab）、资源、讨论，并清理福利羊毛；首页内容流先用带图的普通帖承载，桌面方案的晒图也先用普通帖。
- M2a：首页内容流升级为内容包卡片和一键应用。

## 5. 内容模型

### 5.1 内容类型

沿用资源包的 `kind`，再补上项目、方案、工作流：

| 类型 | 是什么 | 来源 | 能否一键应用 | 阶段 |
| --- | --- | --- | --- | --- |
| `project` | 一个开源项目或产品的解读页（来自 GitHub 或网络发现） | 采集 / 检索 + 编辑 | 不能直接应用；若是 MCP/技能，关联到市场条目，走安装流程 | M1 |
| `effect` | 桌面特效（纯 JSON 数据，无代码） | 用户 | 能（T2 起） | M2 |
| `scheme` | 桌面方案：引用若干已发布内容的清单 | 用户 | 能，逐项导入 | M2 |
| `wallpaper` | 动态壁纸（自包含 HTML） | 用户 / 官方 | 审核后（T1 起） | M3 |
| `widget` | 桌面组件（自包含 HTML） | 用户 / 官方 | 审核后（T1 起） | M3 |
| `game` | 小游戏（文本文件加素材） | 用户 / 官方 | 审核后（T1 起） | M3 |
| `workflow` | Agent 工作流：说明 + 提示词模板 + 引用的技能/连接器 | 官方 / 用户 | 导入到 Agent，技能安装逐次审批 | 官方 M2a，用户 M3 |
| `task` | 任务模板：一段可直接交给助手的任务，含适用场景、提示词、所需技能/连接器、预期产出与风险说明 | 官方 / 用户 | “让助手试试”：唤起桌面端确认后在新对话里开始，写操作仍按权限模式确认 | 官方 M2a，用户 M3 |
| `routine` | 例行事项：按时间自动运行的只读任务（对应桌面端“关怀提醒”里的 `agent` 类规则）：提示词、时间与重复、预期产出 | 官方 / 用户 | “订阅到我的助手”：桌面端展示完整提示词、时间和权限，确认后创建规则 | 官方 M2a，用户 M3 |
| `reminder` | 提醒规则：文字、时间与重复、免打扰（对应关怀提醒的普通规则，纯数据，不运行 Agent） | 官方 / 用户 | 能，T2 起（提议） | 官方 M2a，用户 M2b |
| `goal` | 目标模板：长期目标的结构化描述（结果、验收方式、约束、边界、停止条件），用于“制定与生成规划” | 官方 / 用户 | “用这个目标开始”：填入桌面端长期目标表单，确认后创建 | 官方 M3 |
| `skill` / `expert` / `connector` | 市场里已审核的技能、专家、连接器在社区的展示卡 | 市场目录 | 能：沿用市场的深链安装与审查流程 | M2a |

> 组件脚本能否在打包后的应用里执行，资源包文档标注“尚未实测”，近期有提交修复了自定义组件脚本的沙箱问题。M3 开放 `widget` 的一键应用前，必须先在打包版上实测并更新该文档。

### 5.2 信任分级与放行规则

| 级别 | 含义 | 可一键应用的类型 | 获得方式 |
| --- | --- | --- | --- |
| T0 官方 | 站方制作或编辑 | 全部 | 站方发布 |
| T1 已审核 | 通过人工审核的用户内容 | 全部资源包类型 | 审核队列通过 |
| T2 用户未审 | 用户刚发布，仅过自动检查 | **仅 `effect`、`scheme`**（纯数据，已确认）；`reminder` 同为纯数据，提议一并放开 | 自动 |

规则：

- **T2 的 `effect`、`scheme` 无需人工审核即可一键应用**（已确认），发布时仍过自动检查，可被举报并下架。
- `wallpaper`、`widget`、`game`、`workflow`、`task`、`routine`、`goal` 默认只能“下载或复制后手动使用”（装扮部分与现状一致），审核通过后才出现“一键应用”“让助手试试”或“订阅”按钮。任务模板和工作流能驱动有写权限的 Agent；例行事项虽然只读，但仍能在用户不在场时读取本机文件并访问网页，所以同样按可执行内容对待。`reminder` 是纯数据，与 `effect` 同级。
- `scheme` 引用的每一项必须是官方内置、T0/T1 内容，或 T2 的 `effect`；引用 T2 的可执行内容一律拒绝。
- 举报、下架会让对应内容立即失去“一键应用”资格；已导入的本地副本不会被远程删除，但桌面端下次打开该内容时提示“来源已下架”。
- 发布者被封禁时，其全部 T1 内容回到待复审。

### 5.3 内容包的标识与校验

- 仍用现有 zip 格式（`manifest.json` 加作品文件），**不新造格式**；`resource-pack-format.md` 是唯一规范。
- 社区侧为每个包记录：`pack_id`、`kind`、版本、`sha256`、大小、预览图、作者、信任级别、状态、应用次数。
- 服务端接收时重新校验 manifest 和文件规则。服务端与桌面端各有一份校验逻辑，**必须共用同一组测试向量**，防止一边放行、一边拒绝。

### 5.4 一键应用协议

复用已有的深链机制，新增社区命名空间：

```text
xiaoban://community/apply/{kind}/{pack_id}?version=&sha256=
```

流程：

1. 论坛页或手机端点“应用到我的桌面”，唤起桌面端。
2. 桌面端弹确认窗口：显示名称、作者、信任级别、类型、大小、校验值，以及（对 HTML 类）“该内容包含脚本，将运行在沙箱中”。
3. 用户确认后下载，核对 `sha256`，复用既有导入流程落盘。
4. 导入完成后询问“现在应用吗”，用户再确认一次才真正换壁纸、开特效或摆组件。这与“导入不自动应用”的现有约定一致。
5. 链接永远只唤起确认窗口，不静默执行任何东西。未安装桌面端时，页面给出下载入口，并保留链接。

## 6. 功能需求

### 6.1 发现与周刊：热榜研究与项目话题（F1，M1）

**目的**：用每周新项目和新产品的中文解读给社区提供稳定的种子内容，同时作为生产力侧的入口。选题标准是“值得看、能行动”，不限于 GitHub：好内容常常能破圈，把圈外的人带进社区。

**选题范围与来源**

选题不按平台划分，按“值得看、可行动、有破圈潜力”划分。破圈内容（圈外也在讨论的产品、现象级项目、好用的小工具）能把开发者以外的人带进来，价值往往高于纯圈内新闻；但仍要和“数字生活、桌面、效率、创作”相关，并尽量有可以采取的动作。

三类来源，职责不同：

| 来源类型 | 例子 | 用途 | 用法限制 |
| --- | --- | --- | --- |
| 一手事实 | GitHub 仓库与接口（star、提交、许可证、README）、发布页、官方文档 | 所有事实性陈述的依据 | 事实只取一手来源 |
| 发现信号 | GitHub 近期新增 star 的搜索结果、Hacker News、Reddit、Product Hunt、Hugging Face 趋势、V2EX / 少数派 / 掘金等中文社区、搜索引擎对近期关键词的检索 | 发现候选，判断热度和破圈程度 | 只当线索，不当正文 |
| 二手评论 | 博客、媒体报道、社区讨论 | 了解反应、找角度 | 仅参考，不转述、不洗稿；引用须短并附链接 |

规则：

- **跨来源互证**：候选尽量有两个以上互相独立的信号（例如 GitHub 增长加一处社区讨论）。刷量很难同时伪造独立讨论，所以这也是对“疑似刷量”的一道防线。
- **事实回到一手来源核实**：版本、价格、许可证、功能以官方页面为准；无法核实的写“未核实”或干脆不收。
- **抖音、微信公众号等封闭平台**：公开页面的抓取受平台条款限制，M1 不做自动采集；编辑看到好线索可人工提报，自行核实后写入。
- GitHub 没有官方的 Trending 接口。候选集用搜索接口按近期新增 star、创建时间等近似得出，口径、限频和稳定性**需要先小范围实测**。
- 人工提报：编辑可直接粘贴仓库或网页地址。

**M1 的实现路径：先用本地技能，不先建服务端采集器**

- 论坛已有本地技能 `forum-post-studio`，覆盖“选题、资料核实、创作、配图、校验、导入为待发布稿、发布”的全流程，使用站方编辑令牌，默认只导入待发布稿，由你决定是否发布。M1 的周刊直接在这套流程上增加“周刊”工作模式（选题清单模板、来源分层与互证检查、固定的稿件结构），**不需要新增服务端代码**。
- 联网检索先用本地的搜索与浏览能力；`server-ai` 已规划联网搜索接口（`/v1/search`、`/v1/fetch`，该服务尚未部署），需要定时、批量或无人值守时再接入。
- 服务端采集器（在市场采集工作台新增 GitHub 与网页来源）放到周刊稳定、量变大之后再做，不作为 M1 前置。
- M1 先以普通 Markdown 帖发布周刊和单项目解读；结构化的 `projects` 扩展与“试用”类行动按钮，在周刊稳定后加入。

**过滤（进入候选前）**

| 规则 | 说明 |
| --- | --- |
| 基本健康度 | 有 README、有许可证声明或明确标注“无许可证”、近期有提交 |
| 异常增长 | star 增速异常的项目标记“疑似刷量”，只进人工复核，不自动上榜 |
| 安全标记 | 包含安装即执行脚本、要求高权限、依赖来源不明等，在页面显式提示 |
| 类型 | 标注 MCP / 技能 / 命令行工具 / 库 / 框架 / 应用 / 产品或网站 / 模型 / 其他 |
| 破圈潜力 | 圈外是否也在讨论、普通用户能否看懂和上手；作为排序加分项，不作为入选条件 |

**解读**

- 每个项目的解读**只生成一次，全站共享**，不对每个用户重复生成，以控制成本。M1 由本地 AI 起草，你审核后发布。
- 固定结构：它是什么（一句话）、适合谁、能做什么、怎么上手、风险与局限、在国内的可用性（网络、模型或服务依赖）。
- 页面显著标注“AI 整理，编辑审核”。**未经编辑审核的解读不上榜。**
- README、网页和评论文本一律视为不可信数据：不让其中的指令影响解读流程（网页来源比仓库更容易夹带注入），不转存代码，只做摘要和链接，遵守来源许可证。
- **写自己的话**：事实取自一手来源；二手文章只作参考，不改写、不拼接，引用要短并附链接。大量改写他人文章有版权风险，也会削弱页面本身的价值。

**项目页**

- 每个入选项目对应一个论坛话题（沿用 `topics`，加 `project` 扩展），用户在下面讨论。
- 页面输出 SEO 友好的 HTML，沿用论坛现有的服务端渲染。
- 行动按钮由类型决定：

| 类型 | 按钮 |
| --- | --- |
| MCP / 技能（已有市场条目） | “让小伴试用”：深链到市场的确认窗口，走现有审查、哈希锁定和逐次审批 |
| 命令行工具 | “记录到资料库”（本地），运行需用户在 Agent 中批准 |
| 库 / 框架 / 模型 / 论文 | “记录到资料库” |

“记录到资料库”写入桌面端本地资料库，不上传，沿用“本地数据不得自动发送到 API”的原则。

**周刊**

- 每周一发布一期，10 条以内，附一句编辑点评。AI 负责采集、初筛、解读和海报草稿，**发布由你逐期人工确认，不自动发布**；每期条数以你能审完为准，宁可少、不凑数。
- 发布走论坛已有的站方批量发帖链路（编辑令牌、待发布稿、`forum-post-studio`），不新建发布通道。
- 每期自动生成分享海报（竖版图），供站外传播；M1 可先手工制作。

**验收**

- 连续 4 周按时发布，每期至少 8 条通过人工终审。
- 抽查 20 个项目页：无将原文大段转载，无未标注的 AI 内容，类型与行动按钮匹配。
- 疑似刷量项目没有未经复核上榜。
- 每期至少有 1–2 条非开发者也看得懂的“破圈”选题（初值）。
- 每条解读的事实陈述都能在一手来源里找到对应出处。

### 6.2 内容包发布与一键应用（F2，M2–M3）

**发布**

- 桌面端“分享到论坛”升级为“发布到社区”：应用内登录态直接上传 zip，自动截取预览图，选择标签后发布，不再需要手动去论坛填表。现有的“导出资源包”“打开论坛”保留作为后备。
- 论坛新增“内容包帖”：除正文外展示类型、预览图（`wallpaper`/`widget`/`game` 可附短录屏）、版本、大小、校验值、权限说明（来自 manifest）、应用次数、“应用到我的桌面”按钮。
- 内容包按类型归入首页内容流（§4.2），用类型和标签细分，不再沿用按产品划分的“小伴壁纸”“小伴游戏”板块，也不新开一套社区。

**在线试玩与预览**

- 游戏详情页提供“在线试玩”，特效、壁纸、组件提供网页预览。游戏包本身是自包含 HTML，并有存档与成绩协议，网页端已有沙箱游戏包可参考。
- **只对官方和已审核（T0、T1）的内容开放。** 未审核的内容只能看预览图和下载，不能在线运行。
- **必须放在独立的沙箱域名**，iframe 不给同源权限，与站点登录态隔离。论坛现有的附件一律按下载输出、不让浏览器直接打开，这个原则不变。
- **内容包要走专门的上传和存储，不走论坛附件通道。** 论坛附件上限成员 5 MB，而游戏包可能带音频和图片，上限更大；沿用资源包 32 MB 的规则，并单独设容量与限流。
- 在线试玩的成绩可用于周挑战和排行榜（§6.5）。

**自动检查**

- manifest 校验、体积、文件类型、重复检测（按内容哈希）。
- HTML 类额外扫描：外部网络请求、动态执行字符串、对宿主的越权消息。命中则进入人工审核队列，不命中也保持 T2，需审核才升级 T1。
- 文本与预览图过敏感词和图片审核（论坛“二期未做”的敏感词需先补，见 M2b）。

**应用与统计**

- 按 §5.4 流程应用。应用次数按“成功导入”计，匿名累计，不关联到用户。
- 内容详情显示“被应用 N 次”，用于排序与创作者反馈。

**派生与复刻**（M3）：发布时可标注来源包，作者页显示“被复刻”次数。

### 6.3 桌面方案（F3，M2）

**是什么**：一份清单，记录“这套桌面由哪些内容组成”。

```text
scheme: { name, preview, items: [ { kind, ref, params? } ] }
  - wallpaper  ref → 壁纸站内容 或 已发布内容包
  - effect     ref + 参数（密度、速度、大小）
  - widgets[]  ref + 位置与尺寸（相对屏幕比例）
  - companion  ref（主题）
```

- 方案本身不含可执行内容，只含引用和参数。
- 桌面端“保存当前桌面为方案”：读取当前壁纸、特效、组件布局，生成清单和截图。该功能依赖 PRD_小伴桌面里的“场景搭配与收藏”（本地），如未实现，先做本地版。
- 复刻：逐项检查是否已有，缺的按 §5.4 下载导入，最后询问是否一键应用整套；任何一项被下架或不可用，提示替代而不是整体失败。
- 多显示器、分辨率差异：布局按比例还原，不保证与原图一致，页面写明。

**验收**：在另一台机器上，从一个含壁纸、特效和两个组件的方案点“复刻”，三次确认内完成，且不静默应用任何内容。

### 6.4 助手能力：技能、例行、目标、任务与成果展示（F4，M2a 起）

**为什么要有这一节**：社区如果只展示装扮，产品会像一个壁纸站，助手真正的工作能力（读写文件、搜索、运行命令、网页、技能与连接器、操作电脑）没有人看到。能力要和装扮并列，可看、可试。

形态如下：

1. **能力卡**（M2a，不依赖用户量）：把市场里已审核的技能、专家、连接器做成社区卡片，附一句话说明、示例产出和风险说明。市场已有 `xiaoban://market/install/...` 深链，按钮沿用其审查、哈希锁定、逐次批准的安装流程。由官方挑选。
2. **任务模板**（官方 M2a，用户 M3）：一个可直接交给助手的任务，如“整理下载文件夹”“把会议录音写成纪要”“汇总几份表格”。结构：标题、适用场景、提示词、所需技能或连接器、预期产出、风险说明、已验证的版本。按钮“让助手试试”：唤起桌面端，**完整展示将发给助手的提示词和所需权限**，用户确认后在新对话里开始；写文件、运行命令仍按当前权限模式逐次确认，模板不能绕过。
3. **成果展示**（M2b 起）：帖子形态，展示“助手做了什么”：任务、前后对比、用到的技能，附任务模板方便复刻。这是向办公用户证明能力最直接的内容。
4. **例行事项与提醒规则**（官方 M2a；用户发布的提醒规则 M2b、例行事项 M3）：把桌面端“关怀提醒”里已有的两类规则做成可订阅内容，它们也是让人每天打开助手的理由（路线图的“主动性”方向）。
   - 提醒规则是纯数据。
   - 例行事项是到点自动运行的任务。**按现有实现它只有读取类工具**（读工作目录文件、搜索、看时间、打开网页），有轮次与调用上限，结果显示在桌面提醒气泡，创建时即使在“完全信任”下也要用户确认。因此社区里的例行事项只能是“读取、汇总、提醒”类，如“每天早上给我一份行业新闻简报”“每周五汇总本周待办”，不能自动写文件或运行命令；需要这些的，引导用户改用任务模板手动触发。
   - 订阅时桌面端完整展示提示词、时间和权限，确认后才创建。
   - 例行事项能在用户不在场时读本机文件并访问网页，存在“读到的内容经网页地址带出去”的外泄可能，**需先评估现有网页访问工具对此的约束**；评估前只上线官方例行事项。
5. **目标模板**（官方 M3）：把长期目标（结果、验收方式、约束、边界、停止条件）做成可套用的模板，用于“制定与生成规划”，如“四周内完成开题报告”“三个月学完某门课”。点击“用这个目标开始”，填入桌面端的长期目标表单，用户确认后创建。目标里的“验证命令”是可执行命令，**模板不携带该字段**，由用户自己填写。
6. **对话角色**：市场里的专家已经是这类内容，由能力卡覆盖；社区只做展示与讨论，不另建体系。

要求与限制：

- **官方任务模板上线前必须实测**，并写明在哪个版本验证过。Agent 的办公产出质量仍在改进（路线图列有评测集计划），不宣传未验证的效果。
- 模板本身是文本，不携带脚本。引用的技能不在市场目录的，提示“尚未审核，无法一键安装”，可去市场申请收录。
- 用户发布的任务模板和工作流先是 T2：只能查看和复制，审核通过（T1）后才出现“让助手试试”。
- **这些类型在桌面端目前没有导入入口**（资源包导入只支持壁纸、特效、组件、游戏）。需要新增“订阅 / 套用”能力；格式沿用 zip 加 `manifest.json` 的 `kind`，抬高 `schemaVersion`，旧版本遇到会提示更新。

### 6.5 求助与挑战（F5，M3）

- **需求求助**：在讨论里新增分类“求助”（“我想要一个……”）。需求方描述想要的组件、特效或方案，创作者交付内容包帖作为回答，需求方可随时**采纳**一条回答，帖子标记为已解决；设置求助期限，到期未采纳标为未解决。**不挂积分、不显示奖励**。
- **主题挑战**：官方每周发主题帖；投稿为带挑战标签的内容包帖；投票用点赞；截止后站方精选置顶。结算不涉及积分。
- **积分先不外露**：论坛既有的积分后端（新用户、签到、邀请、附件定价等）保留，新前台和手机应用的界面里**不出现积分、悬赏金额、兑换入口**。等奖励机制设计好、并有防刷分方案后再对外，届时“求助”可以再加悬赏。

### 6.6 账号与云端沉淀（F6，M3）

| 对象 | 是否同步 | 说明 |
| --- | --- | --- |
| 桌面方案 | 是（用户开启） | 换机恢复，手机端可查看、一键“发到电脑” |
| 自己发布的内容包 | 是（已发布即在云端） | “我的作品”页即备份 |
| 收藏（内容、项目） | 是 | 手机与桌面共享 |
| 壁纸/设置/小游戏存档 | 否（首版） | 保持本地优先，后续单独评估 |
| Agent 记忆、资料库 | **否** | 隐私敏感，且本地库明确不自动上传；若要同步需另立项并默认端到端加密 |

- 所有同步为**用户主动开启**，默认关闭，设置页写明同步哪些、存在哪里。
- 不登录也能使用桌面端全部本地功能，不为社区而增加基础功能的账号门槛。
- **存储**：同步数据先放自有服务器，按用户设容量上限和单文件上限；上线前必须有定期备份和恢复演练，否则““我的作品”页即备份”不成立。换大容量机型之前，先把同步对象限制在方案清单和已发布内容包等小体积数据。云服务器资源有限，按仓库部署规范在本地构建后上传，不在服务器上编译。

### 6.7 桌面端入口（M1 起）

- 控制台新增“社区”页：本周周刊、热门内容包、我的发布、收藏、一键应用入口。
- 首次进入时提示一次，之后不弹窗打扰；周刊更新使用已有的公告/消息机制，不新增常驻弹出。
- 超级小伴可以推荐内容，必须遵守 `agent-proactivity` 的授权、免打扰和每日预算，**默认关闭**。

### 6.8 运营后台

在论坛后台新增：

- 内容包审核队列（自动检查结果、预览、权限说明、通过/驳回/要求修改）。
- 周刊编辑（候选项目池、解读审核、排序、点评、发布）。
- 项目库管理、精选与置顶、挑战管理。
- 漏斗看板（§8），按类型与栏目拆分。

### 6.9 移动端（F7，分阶段）

手机的定位以[路线图](../../client/xiaoban-desktop-wallpaper/docs/assistant-roadmap.md)为准：电脑上小伴的遥控器和收集口，不做第二个完整 Agent。社区相关部分如下。

**应用结构（原型已出第一版）**

底栏五格，从左到右：

| 入口 | 内容 |
| --- | --- |
| 小伴AI | 先进“小伴AI 首页”（AI 功能入口），再进对话页；对话、问答、轻量办公，装扮设计与游戏创作也在对话里完成（§6.10）；另有“我的电脑”（配对状态、任务、发到电脑） |
| 游戏 | 官方游戏与社区游戏，在线试玩，排行榜 |
| 发布（中间的“+”） | 不是页面，是动作入口：点开面板，选“用 AI 创作”（进入对话页）、“发布已有作品”（选资源包 zip）、“发帖”。样式与其他格子完全一致：未选中是灰色的“+”，点开后变成红色胶囊“发布”，其余格子回到未选中 |
| 社区 | 顶部横排一级栏目：首页 / 资源 / 讨论（§4.2）；周刊在首页的二级 Tab 里 |
| 我的 | 我的作品、收藏、收件箱状态、模型与额度、设置与账号 |

**这是一个新应用，现有的壁纸 App 保持独立**（已确认）。新应用以 `xiaoban-multiplatform` 为起点（路线图已定），是新工程，不与壁纸 App 合并，也不共享源码（仓库允许重复代码）；壁纸 App 继续负责壁纸的浏览与下载。两者共用统一账号，并可以互相导流（提议）：壁纸 App 里放社区入口，社区里的壁纸内容可跳转壁纸 App，它是现成的入口层。

创作不单独占一级入口，也不是对话之外的“模式”：创作本来就是“一句话描述”的对话行为，与桌面端“用 Agent 工具创作”一致，并共用 server-ai 的额度。生成结果以卡片的形式出现在对话里，带预览、电脑屏幕比例切换，以及“调整 / 发布到社区 / 发到电脑”。“我的作品”入口放在小伴AI和“我的”里。

**小伴AI：首页与对话页**

- **首页是 AI 功能的入口，不是聊天窗口。** 从上到下：问候与一句说明；输入入口卡（点一下进入对话页，卡上摆着附件、当前模型、语音输入、实时对话、发送）；功能入口六格（做装扮、做小游戏、设提醒、定时任务、做计划、我的电脑）；最近对话；我的作品。左上角按钮打开侧栏。问答不单设入口（点输入卡就是问答），拍照在附件里选“相机”，语音和实时对话就是输入卡上的两个按钮，所以不再重复放入口。
- **对话页是单独的页面**，不带底栏，专注对话。顶栏：返回首页、标题与剩余额度、新对话、对话列表。生成结果以卡片出现在对话里（§6.10）。
- **输入区分两行**：上面是输入框，下面是工具栏，从左到右为：附件（相机、相册、文件、资料库）、模型按钮（显示当前模型，点开选择，见下）、联网开关、语音输入、实时对话、发送。
- **侧栏**从左边滑出，首页和对话页都有：首页的侧栏：新对话、搜索、最近对话、我的作品、设置；对话页的侧栏：新对话、搜索、最近对话、我的作品。“我的电脑”只放在首页功能入口和“我的”页，不在侧栏重复。
- **模型：对话里选，“模型与额度”页配**（对齐桌面端的模型配置，实现在 `client/xiaoban-desktop-wallpaper` 的 `AiConfigCard.vue`、`ai_config.rs`）：
  - 输入框里的模型按钮点开一个底部面板，只对当前对话生效：上半是小伴AI 下发的模型列表（按名称显示，每项有一句说明；当前账号用不了的灰显，写明“兑换付费额度后可用”；支持调节思考强度的模型，名字后面跟一个“思考 · 当前强度 ›”按钮，点开弹出“思考强度”小弹窗，选一档后同时选中该模型并关闭菜单；不支持的模型不显示这个按钮），下半是用户自己配好的模型服务。面板底部链接到“模型与额度”。桌面端也是同样的做法（输入框里切换，设置里配置）。
  - “模型与额度”页从“我的”进入，页面本身只做概览，配置都在弹窗（底部面板）里完成，不往一页里塞：小伴AI 一张卡片（当前模型、剩余额度、到期时间，按钮“配置”“启用”），下面是各家模型服务的列表（名称、当前模型、状态）；点“配置”或点某一行，各自弹出配置面板。分两块。**小伴AI（官方）的弹窗**：剩余额度、到期时间、兑换码，以及小伴AI 下发的“可用模型”列表（单选默认模型，推荐项带标记，支持调节的模型后面同样有“思考 · 当前强度 ›”，点开选思考强度）；列表由 `server-ai` 的 `GET /api/ai/tiers` 下发，名称、说明、排序、是否需要付费、可用的思考等级都由后台维护，客户端不写死；它跟着账号走，换设备自动同步，不需要用户填地址和密钥，**自己的模型服务的弹窗**：DeepSeek、智谱、Kimi、MiniMax 四家加“自定义供应商（OpenAI 兼容）”，点进去填接口协议、API 地址、密钥，可测试连接、拉取可用模型、选默认模型。
  - **自己的密钥只保存在手机本机，不上传，也不同步到电脑**（与桌面端一致：密钥只存本机，云端同步不带密钥），换手机要重新填。
  - 手机上不做的高级项：思考等级声明、思考摘要、Messages 思考模式与预算、单次输出上限、上下文上限与智能压缩；写明“请在电脑上设置”。
  - 原型里第一块的“实时对话单次时长上限”不做；“默认模式”从设置页移到这里。
- **资料库**（对齐桌面端资料库，实现在 `client/xiaoban-desktop-wallpaper/src/ui/pages/LibraryPage.vue`，桌面端有“我的文档 / 云文档 / 收藏 / 记忆”四个标签）：
  - 手机上做两个标签：**我的文档**（拍照、相册、文件、新建文本；文件夹，列表里显示类型、大小、读取状态——读取中、不支持、文件过大会标出来）和**收藏**（对话里存下来的回答、文字、图片、截图，注明来自哪个对话）。云文档链接和“记忆”首版不做：记忆依赖桌面端 Agent 的记忆机制，手机上目前是云端问答，没有对应物。
  - **只保存在手机本机，暂时不与电脑同步，也不上传**；页面顶部写明这一点。要不要同步、怎么同步以后再设计（涉及隐私、容量、冲突）。
  - **可以被小伴AI 读取**：在对话页输入框的附件里选“资料库”，勾选资料后发给小伴AI；选择面板里明确提示“所选内容会发送到云端模型来回答，不会同步到电脑”，每次发送前都要用户自己勾选，不做自动读取。读取中、读取失败的资料不能选。
  - 入口：“我的”页的列表、小伴AI 首页和对话页的侧栏，以及对话页附件里的“资料库”。
- **有几个入口是占位**：首页的“我的电脑”，对应路线图里尚未实现的能力（遥控电脑上的 Agent）；“联网”开关桌面端目前没有。“设提醒”“定时任务”“做计划”对应桌面端已有的关怀提醒、定时只读任务和长期目标，手机上先在对话里生成，再发到电脑订阅（运行位置在电脑端，与能力详情页一致）。原型把它们画出来是为了确定位置，是否随首版上线见 §13。

**实时对话**（对齐桌面端[语音引擎设计](../../client/xiaoban-desktop-wallpaper/docs/design-specs/voice-engine.md)）：

- **两个按钮分工**：麦克风是语音输入，说完转成文字放进输入框，不自动发送，由用户确认；实时对话是单独的声波按钮，放在发送键左边，发送键始终保留。
- **进行中**：输入区原位变成语音条，不跳页面。从左到右：声波球（在听 / 在想 / 在说 / 已静音）、状态和一句提示、计时、静音、结束；下面一行标明对话方式“实时 · 小伴AI”并提示按分钟消耗额度。标题下的额度换成“实时对话中”。
- **对话记录**：双方的话按普通消息写进对话，用户的话标“语音”，识别中的内容以灰色半透明气泡显示，前后有“实时对话 · 时间 开始”的分隔线。
- **安全**：需要确认的操作（发消息、动文件）仍在卡片上点确认，不接受语音代为确认。
- **依赖**：server-ai 的 `GET /v1/realtime`（网关部分已有，该服务尚未部署）。
- **手机上要另外决定的**（桌面端没有这些问题）：没登录、没网络或额度用完时怎么办，桌面端会退回本机识别，手机端没有本机识别引擎；切后台或锁屏时是否继续，建议默认结束，避免持续扣费；流量与耗电。见 §13。

**发到电脑：首版用系统分享，后期改云端收件箱**

- **首版（已决定先这样，后期要改）**：手机上设计好的装扮导出成资源包 zip，用系统分享发给微信（文件传输助手）等应用，用户自己在电脑上收到后，到桌面端对应页面点“导入资源包”。不需要任何新基础设施：桌面端的导入入口和校验已经存在，导入只落盘、不自动应用。传输方式不影响安全，文件到电脑后同样经过桌面端的完整校验。
- 首版的已知不足：步骤多（保存、传到电脑、手动导入）；依赖电脑上装有同一个聊天工具；聊天工具可能限制扩展名和文件大小，所以导出一律用 `.zip`，是否能顺利发送**需要在微信上实测**（资源包上限 32 MB）。
- **后期方案：云端收件箱。** 作品保存到账号云端，桌面端启动和定期检查时提示“来自手机的 N 个新项目”，用户确认后导入，电脑不在线也能发。它依赖 F6 的云端同步，与“遥控电脑上的 Agent”（路线图第 2 项，需要实时中转）是两件事，可以更早交付。
- 预览要按电脑屏幕：创作时选择电脑屏幕比例（如 16:9、16:10），组件按目标尺寸预览，并提示“与实际桌面可能有差异（图标位置、多显示器）”。

| 阶段 | 内容 | 前置 |
| --- | --- | --- |
| A | 论坛网页做移动端适配，用现有 `xiaoban-multiplatform` 网页壳打包：浏览周刊、项目页、内容包，发帖回复 | M2b 的 UGC 合规项（只读浏览不需要） |
| B | 原生 Compose 页面：社区信息流、内容包预览与收藏、“发到电脑应用”（首版系统分享，后期云端收件箱）、小伴AI 首页与对话页（含附件、联网、语音输入）、云端问答（server-ai）、实时对话（依赖实时网关）、游戏、AI 创作与预览（§6.10） | 中转服务、F6 收藏同步 |
| C | 遥控电脑上的 Agent、审批推送、分享到小伴 | 路线图第 2 项 |

要点：

- **装扮可以在手机上创作和预览，但“应用到手机本身”受系统限制。** 装扮内容是 HTML 或纯数据，创作和预览在手机上可行（§6.10）。但应用到手机桌面：iOS 不允许；Android 桌面小组件不能运行任意 HTML；动态壁纸在部分机型（小米、Redmi）的系统选择器上被丢弃，壁纸 App 早期的动态壁纸方案已因此放弃。所以手机上的“应用”落点是：游戏直接玩；壁纸可导出为图片或视频保存到相册（新应用自己实现，不依赖壁纸 App，**导出是否可行需验证**）；其余内容“发到电脑”。
- **游戏类内容包要支持手机端**（已确认）。游戏本身是自包含 HTML，内容基本可复用，但“天然支持”还差一层宿主：手机端要实现与桌面相同的宿主握手协议（存档、成绩）、安全区、沙箱 WebView 和触摸输入。另有几点：
  - 许多游戏默认用键盘，手机没有键盘。建议在 manifest 增加输入方式声明（字段名待定，需同步更新资源包格式文档），手机端只展示声明支持触摸的游戏。
  - `layer: desktop` 的桌面层游戏不适用于手机。
  - 低端安卓的性能、音频自动播放限制需要实测。
  - iOS 对应用内下载并运行第三方 HTML/脚本有审核规则，**上架前需核实**；在核实前，建议 iOS 只放官方内置游戏。
- iOS 与国内安卓商店上架涉及备案和 UGC 审核要求，细节以各商店规定为准，**需在上架前核实，本文不下结论**。

### 6.10 在线创作（F8，M3 起，提议）

**目的**：让没装桌面端的人也能创作和发布。现在创作装扮只能在桌面端借助 Agent 工具（`effect_create`、`widget_create`、`wallpaper_create`、`game_create`）完成，创作漏斗被“先装桌面端并配好模型”卡住。装扮是 HTML 或纯数据，网页和手机都能跑，所以创作可以前移到网页和手机。

**入口**：手机应用里就是小伴AI的对话，不设单独的“创作模式”或类型选择，由 AI 从用户的话里判断要不要生成（聊着聊着说“那就做一个”即可）；网页上是独立的创作页。两者同一套云端服务和额度。

**流程**：一句话描述 → 云端 AI 生成内容包 → 服务端校验（与桌面端同一套规则，共用测试向量）→ 沙箱预览 → 调整 → 发布 / 导出 zip / 发到电脑应用（首版经系统分享，§6.9）。

**依赖与成本**：

- **云端创作服务**：桌面端的创作工具跑在本机宿主里，网页和手机需要云端等价实现。校验器要在服务端可用（桌面端的校验在 Rust 里，能否抽成共用库**需评估**）。
- **模型成本**：每次创作消耗 server-ai 额度；设试用额度和频率限制，超出需登录或兑换。
- **预览与发布**遵守 §6.2：独立沙箱域名，未审核内容不在主域名运行。
- 手机端以文字输入为主，预览用沙箱 WebView。

**切片**：先做 `effect`（纯 JSON、无代码，生成、校验、预览都最简单，T2 即可一键应用），再扩展到 `scheme`、`widget`，最后 `wallpaper`、`game`（HTML，需审核）。

这是创作飞轮的入口，成本主要是模型额度。建议在 M2b 看到创作者数据后再决定投入。

### 6.11 分享（手机应用）

**目的**：让好内容能被带出社区。分享是拉新的主要渠道之一，要做到“一点就能发出去，收到的人点开就能看”。

**入口**：帖子详情和能力详情的顶部栏、装扮详情和桌面方案详情的预览图右上角、游戏试玩页底部的“分享”按钮。周刊、资源后续按同样方式补。

**分享面板**（底部面板）从上到下：
- 被分享内容的预览条：缩略图、标题、作者与类型。
- 第一行是分享去向：微信好友、朋友圈、QQ、微博、复制链接。微信、QQ、微博靠系统与各平台的分享能力实现，面板上图标统一用灰色线条，不放品牌彩色。
- 第二行是动作：生成海报；装扮、方案、能力类多一个“发到电脑”（沿用 §6.9 的发到电脑流程）；收藏；举报。
- “复制链接”点完面板收起，屏幕下方弹出“链接已复制”的轻提示。

**海报**：一张竖版图，上面是封面、标题、一句说明、作者与使用数，底部是小伴标识、二维码和“长按识别二维码，在小伴里查看完整内容”。提供“保存图片”和“分享给朋友”。首版只做一种简洁样式。

**分享链接与落地页**：每个可分享的内容有一个 H5 链接。收到链接的人在微信里点开，看到的是内容预览页：封面、标题、作者、说明，顶部有“打开 App”，底部有“在小伴里打开”和“下载小伴”。已安装的用户点按钮通过链接直接跳到对应内容；未安装的引导下载。落地页不展示需要登录才能看的内容。**H5 域名、App 的通用链接（Universal Link / App Links）和延迟深链（安装后回到原内容）都是新增的工程项，原型没有覆盖。**

**隐私与规则**：
- 只有已发布、公开的内容能生成对外分享链接；草稿、审核中的内容、资料库里的资料都不能分享。
- 资料库和 Agent 记忆不在分享范围内（§6.9）。
- 游戏的分享链接打开后只展示封面和玩法，不在落地页直接运行，试玩仍在 App 内沙箱里。

## 7. 安全、合规与治理

| 风险 | 控制 |
| --- | --- |
| 恶意内容包（可执行内容） | 分级放行（§5.2）；HTML 类需审核；沙箱运行；应用前确认；下架后失去一键资格；哈希校验 |

| 隐私 | 埋点匿名、可关闭、不采集内容；与“本地优先”承诺一致，并在隐私说明披露 |

## 12. 风险

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 没有用户：社区还不存在 | 项目页没有回复，UGC 起不来 | 前期只做官方供给的内容；M1 以访问信号为准；用壁纸站和桌面端现有用户做首批触达；必要时转为桌面内主动推送 |
| 审核与发布依赖一人 | 周刊断更、审核积压 | AI 起草、人终审；每期条数以一个人能审完为上限；允许断更一期并预告，不为凑数降低质量 |
| 服务端与桌面端校验不一致 | 发布成功但导入失败，或反之 | 共用测试向量；发布时服务端校验以桌面端规则为准 |
| GitHub 数据源不稳定 | 候选缺失、限频 | M0 实测；保留人工提报通道 |
| 洗稿与版权 | 改写他人文章被投诉或页面价值低 | 事实取一手来源、写自己的话、引用短并附链接；沿用论坛的投诉与下架流程 |
| 网页来源的提示注入与事实错误 | 解读被诱导或写错 | 网页文本视为不可信数据；事实回一手来源核实；人工终审 |
| 解读成本 | 模型调用费用 | 每项目只生成一次；限制每周候选量；经 server-ai 统一额度 |
| 方案复刻体验差 | 引用内容缺失、布局错位 | 逐项降级提示；先小范围支持，不承诺像素级一致 |
| 改名成本随时间增加 | 品牌认知积累越多越难改 | 按 §2.4 的做法降低替换成本；M1 结束时回看 |
| 范围蔓延 | 团队 2–3 人，同时做装扮、Agent、社区、手机摊不开 | 严格按阶段顺序，每阶段有退出条件和回看点；进入下一阶段看信号，不按日期 |
| 合规不确定 | 上线被限制 | M1 前出结论；手机上架前核实各商店要求 |

### 待确认
