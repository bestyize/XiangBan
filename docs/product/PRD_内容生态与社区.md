## 1. 背景与问题

### 1.1 已有的基础

| 能力 | 现状 | 来源 |
| --- | --- | --- |
| 资源包 | 桌面端可把自创的动态壁纸、桌面特效、桌面组件、小游戏导出为 zip，也能导入；导入只放进对应位置，不自动应用 | 桌面 README、`resource-pack-format.md` |
| 分享到论坛 | 各页有“分享到论坛”，聊天里的 `community_share` 工具可代办；论坛“小伴壁纸”“小伴游戏”板块对所有人开放发帖 | 桌面 README、论坛 README |
| 深链 | `xiaoban://market/...` 已注册，只唤起确认窗口，从不静默安装；真机未验证 | 市场 README |
| 目录与采集 | 市场服务有采集工作台、暂存区、审核入库，已对接 SkillHub，魔搭待配置 | 市场 README |
| 论坛 | 2026-10-11 部署；信任等级、积分、悬赏、附件、SEO 页面、站方批量发帖工具链（编辑令牌、待发布稿、`forum-post-studio` 技能） | 论坛 README |
| 手机方向 | 路线图已把“手机 App：电脑上小伴的遥控器和收集口”排在第 2 位，经 server-ai 中转 | `assistant-roadmap.md` |

### 1.2 缺口

1. **分享是单向的。** 作者导出 zip、手动传到论坛；浏览者只能下载附件，再自己去桌面端导入。看到好东西到用上它，中间隔着五六步。
2. **内容没有结构。** 论坛帖是文本加附件，没有“类型、预览、版本、校验值、被应用次数”，无法排行、筛选或审核。
3. **用户的沉淀都在本机。** 桌面端本地优先，换电脑或重装即丢失；没有云端的东西，就没有“我的作品”“我的方案”，社区里也没有身份可言。
4. **社区还不存在。** 论坛已部署但尚无用户；没有固定栏目，也没有种子内容。
5. **没有数据。** 商业企划里“当前日活与次日留存”至今是待确认；没有埋点，任何关于拉新和留存的判断都只是假设。
6. **UGC 合规项没补齐。** 论坛 README 的“二期未做”里有站内通知、屏蔽用户、敏感词；这些是手机 App 上架 UGC 类应用的前置条件。

### 1.3 外部参照

Wallpaper Engine 的创意工坊证明这类内容有真实需求，也暴露了开放社区的代价：不良内容、低质量上传，以及有报道称攻击者利用工坊投放恶意文件。结论是**“一键使用”的内容必须分级放行**，不能让任意用户上传的可执行内容直接跑在别人电脑上（见 §7）。

### 1.4 已确认的前提

| 前提 | 对本 PRD 的影响 |
| --- | --- |
| 团队 2–3 人，主要工作由 AI 完成 | 所有流程按“AI 起草、人终审”设计；审核与发布是单点瓶颈，每期产出量以一个人能审完为上限；不设需要随时响应的机制 |
| 论坛还没有用户，没有任何基线 | 前期内容必须由官方供给；开放用户发布、悬赏、挑战要等有访问信号后再做；第一阶段验证“能否带来访问”，不是“能否带来互动” |
| 产品要改名，新名称未定 | 见 §2.4 |
| 云端数据放自己的服务器，之后换大容量机型 | 见 §6.6 |
| 生成式内容合规暂不处理，规模变大后再说 | 记为已接受风险，见 §7 |
| 积分奖励机制未定 | 首版不把积分与有价值的权益挂钩，见 §6.5 |

## 2. 定位与目标

### 2.1 定位

产品是**个人助手 Agent + 桌面装扮**两件事，社区是夹在两者之间的内容层：

- 生产力侧：Agent、技能、连接器、工作流、GitHub 项目研究。
- 装扮侧：壁纸、特效、组件、伙伴、游戏、桌面方案。
- 社区把两侧的内容放在同一个地方分享、讨论，并且**每条内容都有一个动作按钮**（试用、安装、应用、复刻）。

产品将改名，“小伴”降为可选的“伙伴”之一，改名事项见 §2.4。本文用“本产品”“社区”指代，不预设新名称。

### 2.2 目标

| 编号 | 目标 | 衡量 |
| --- | --- | --- |
| G1 | 让社区内容能一键用上 | 内容→应用转化率（§8） |
| G2 | 让创作者的作品有地方发、能被用 | 创作者→发布转化率 |
| G3 | 社区每周有稳定的新内容 | 周刊连续发布周数 |
| G4 | 用户的作品和方案有云端身份 | 登录用户中有云端方案/作品的比例 |
| G5 | 能回答“拉新和留存到底来自哪” | 有 7 日留存基线与分模块使用数据 |

### 2.3 非目标

- 不做付费内容交易、创作者分成、打赏（后续单独立项）。
- 不开放用户上传的**可执行内容**（HTML/脚本类）直接一键应用，除非通过审核（§5.2）。
- 不做短视频托管；分享海报和封面图，视频流量留给外部平台。
- 不做个人微信接入（路线图已决定不做）。
- 不做泛 AI 绘画/闲聊社区的专门运营；论坛已有板块，不追加投入。
- 不在本文规定手机端的 Agent 能力范围，以路线图为准（§6.9）。

### 2.4 改名

- **先定名，再对外发布内容。** 周刊、海报、SEO 页面一旦以旧名称积累，改名后要重来；名称应在 M1 第一期发布前确定。
- **用户可见的部分随新名称改**：产品名、站点名、网页与应用文案、海报、域名。
- **技术标识先不改，新旧并存**：`xiaoban://` 深链（新增新名称协议、保留旧协议兼容）、`~/.xiaobanwallpaper` 数据目录（不迁移）、`xiaoban-community` 内置技能、包名与账号中心 `client_id`。理由是这些改动风险高、用户看不见，且已安装的旧版本仍在使用。
- **商标、域名、应用商店重名需要自查**，本文没有核查。现有对外名称有“小伴桌面”“相伴”“超级小伴”等，改名时要一并梳理。

## 3. 用户

| 用户 | 要什么 | 在社区里的主要动作 |
| --- | --- | --- |
| 装扮党 | 好看的桌面，不想折腾 | 逛、复刻桌面方案、收藏 |
| 办公效率用户 | 少做重复事 | 看项目周刊、装技能、导入工作流 |
| 开发者 / AI 玩家 | 追新项目，试新工具 | 看热榜解读、讨论、分享自己的项目 |
| 创作者 | 做出东西被人用 | 用 AI 或手工做内容包、发布、看被应用次数 |
| 手机轻用户 | 碎片时间 | 刷社区、问答、玩游戏，把东西“发到电脑” |

## 4. 产品结构

```text
入口层（拉新）      壁纸站 · 内容包预览 · 热榜 SEO 页 · 周榜海报
日常层（留存）      关怀提醒 · 小组件 · 专注 · Agent 日常任务
沉淀层（深留存）    账号云端：桌面方案 · 作品备份 · 收藏
关系层（放大器）    社区：项目话题 · 内容包 · 桌面方案 · 悬赏 · 挑战 · 创作者
```

各层的作用：入口层负责被看见；日常层给每天打开的理由；沉淀层让用户越用越离不开；关系层把前三层的内容变成可传播、可协作的东西。

### 4.1 栏目节奏

固定节奏让用户知道什么时候该来。受限于一个人终审，**M1 只做周一的热榜周刊**，其余栏目在有稳定内容来源后依次加入。初值如下。

| 日 | 栏目 | 内容 | 主要来源 |
| --- | --- | --- | --- |
| 周一 | 热榜周刊 | 本周值得看的开源项目，10 条以内 | 采集 + 解读 + 人工终审（§6.1） |
| 周三 | 创作精选 | 本周被应用最多或编辑挑选的内容包 | 用户 + 编辑 |
| 周五 | 桌面方案 | 精选桌面方案，可复刻 | 用户 + 编辑 |
| 周末 | 主题挑战 | 官方出题，投稿与投票 | 用户 |

## 5. 内容模型

### 5.1 内容类型

沿用资源包的 `kind`，再补上项目、方案、工作流：

| 类型 | 是什么 | 来源 | 能否一键应用 | 阶段 |
| --- | --- | --- | --- | --- |
| `project` | 一个开源项目的解读页 | 采集 + 编辑 | 不能直接应用；若是 MCP/技能，关联到市场条目，走安装流程 | M1 |
| `effect` | 桌面特效（纯 JSON 数据，无代码） | 用户 | 能（T2 起） | M2 |
| `scheme` | 桌面方案：引用若干已发布内容的清单 | 用户 | 能，逐项导入 | M2 |
| `wallpaper` | 动态壁纸（自包含 HTML） | 用户 / 官方 | 审核后（T1 起） | M3 |
| `widget` | 桌面组件（自包含 HTML） | 用户 / 官方 | 审核后（T1 起） | M3 |
| `game` | 小游戏（文本文件加素材） | 用户 / 官方 | 审核后（T1 起） | M3 |
| `workflow` | Agent 工作流：说明 + 提示词模板 + 引用的技能/连接器 | 用户 | 导入到 Agent，技能安装逐次审批 | M3 |

> 组件脚本能否在打包后的应用里执行，资源包文档标注“尚未实测”，近期有提交修复了自定义组件脚本的沙箱问题。M3 开放 `widget` 的一键应用前，必须先在打包版上实测并更新该文档。

### 5.2 信任分级与放行规则

| 级别 | 含义 | 可一键应用的类型 | 获得方式 |
| --- | --- | --- | --- |
| T0 官方 | 站方制作或编辑 | 全部 | 站方发布 |
| T1 已审核 | 通过人工审核的用户内容 | 全部资源包类型 | 审核队列通过 |
| T2 用户未审 | 用户刚发布，仅过自动检查 | **仅 `effect`、`scheme`**（纯数据） | 自动 |

规则：

- **T2 的 `effect`、`scheme` 无需人工审核即可一键应用**（已确认），发布时仍过自动检查，可被举报并下架。
- `wallpaper`、`widget`、`game`、`workflow` 默认只能“下载后手动导入”（与现状一致），审核通过后才出现“一键应用”按钮。
- `scheme` 引用的每一项必须是官方内置、T0/T1 内容，或 T2 的 `effect`；引用 T2 的可执行内容一律拒绝。
- 举报、下架会让对应内容立即失去“一键应用”资格；已导入的本地副本不会被远程删除，但桌面端下次打开该内容时提示“来源已下架”。
- 发布者被封禁时，其全部 T1 内容回到待复审。

### 5.3 内容包的标识与校验

- 仍用现有 zip 格式（`manifest.json` 加作品文件），**不新造格式**；`resource-pack-format.md` 是唯一规范。
- 社区侧为每个包记录：`pack_id`、`kind`、版本、`sha256`、大小、预览图、作者、信任级别、状态、应用次数。
- 服务端接收时重新校验 manifest 和文件规则。服务端与桌面端各有一份校验逻辑，**必须共用同一组测试向量**，防止一边放行、一边拒绝。

### 5.4 一键应用协议

复用已有的深链机制，新增社区命名空间：

```text
xiaoban://community/apply/{kind}/{pack_id}?version=&sha256=
```

流程：

1. 论坛页或手机端点“应用到我的桌面”，唤起桌面端。
2. 桌面端弹确认窗口：显示名称、作者、信任级别、类型、大小、校验值，以及（对 HTML 类）“该内容包含脚本，将运行在沙箱中”。
3. 用户确认后下载，核对 `sha256`，复用既有导入流程落盘。
4. 导入完成后询问“现在应用吗”，用户再确认一次才真正换壁纸、开特效或摆组件。这与“导入不自动应用”的现有约定一致。
5. 链接永远只唤起确认窗口，不静默执行任何东西。未安装桌面端时，页面给出下载入口，并保留链接。

## 6. 功能需求

### 6.1 热榜研究与项目话题（F1，M1）

**目的**：用每周新项目的中文解读给社区提供稳定的种子内容，同时作为生产力侧的入口。

**采集**

- 在市场采集器里新增 GitHub 来源，产出“候选项目”进入暂存区；沿用其“采集 → 暂存 → 人工审核 → 入库”的流程。
- GitHub 没有官方的 Trending 接口。候选集用搜索接口按近期新增 star、创建时间等近似得出，具体口径、限频和稳定性**需要先小范围实测**，作为 M1 的第一项任务。
- 辅以人工提报：编辑可直接粘贴仓库地址。

**过滤（进入候选前）**

| 规则 | 说明 |
| --- | --- |
| 基本健康度 | 有 README、有许可证声明或明确标注“无许可证”、近期有提交 |
| 异常增长 | star 增速异常的项目标记“疑似刷量”，只进人工复核，不自动上榜 |
| 安全标记 | 包含安装即执行脚本、要求高权限、依赖来源不明等，在页面显式提示 |
| 类型 | 标注 MCP / 技能 / 命令行工具 / 库 / 框架 / 应用 / 模型 / 其他 |

**解读**

- 服务端用大模型对每个项目**生成一次，全站共享**，不对每个用户重复生成，以控制成本。
- 固定结构：它是什么（一句话）、适合谁、能做什么、怎么上手、风险与局限、在国内的可用性（网络、模型或服务依赖）。
- 页面显著标注“AI 整理，编辑审核”。**未经编辑审核的解读不上榜。**
- README 和仓库内文本一律视为不可信数据：不让其中的指令影响解读流程，不转存代码，只做摘要和链接，遵守来源许可证。

**项目页**

- 每个入选项目对应一个论坛话题（沿用 `topics`，加 `project` 扩展），用户在下面讨论。
- 页面输出 SEO 友好的 HTML，沿用论坛现有的服务端渲染。
- 行动按钮由类型决定：

| 类型 | 按钮 |
| --- | --- |
| MCP / 技能（已有市场条目） | “让小伴试用”：深链到市场的确认窗口，走现有审查、哈希锁定和逐次审批 |
| 命令行工具 | “记录到资料库”（本地），运行需用户在 Agent 中批准 |
| 库 / 框架 / 模型 / 论文 | “记录到资料库” |

“记录到资料库”写入桌面端本地资料库，不上传，沿用“本地数据不得自动发送到 API”的原则。

**周刊**

- 每周一发布一期，10 条以内，附一句编辑点评。AI 负责采集、初筛、解读和海报草稿，**发布由你逐期人工确认，不自动发布**；每期条数以你能审完为准，宁可少、不凑数。
- 发布走论坛已有的站方批量发帖链路（编辑令牌、待发布稿、`forum-post-studio`），不新建发布通道。
- 每期自动生成分享海报（竖版图），供站外传播；M1 可先手工制作。

**验收**

- 连续 4 周按时发布，每期至少 8 条通过人工终审。
- 抽查 20 个项目页：无将原文大段转载，无未标注的 AI 内容，类型与行动按钮匹配。
- 疑似刷量项目没有未经复核上榜。

### 6.2 内容包发布与一键应用（F2，M2–M3）

**发布**

- 桌面端“分享到论坛”升级为“发布到社区”：应用内登录态直接上传 zip，自动截取预览图，选择标签后发布，不再需要手动去论坛填表。现有的“导出资源包”“打开论坛”保留作为后备。
- 论坛新增“内容包帖”：除正文外展示类型、预览图（`wallpaper`/`widget`/`game` 可附短录屏）、版本、大小、校验值、权限说明（来自 manifest）、应用次数、“应用到我的桌面”按钮。
- 沿用 `小伴壁纸`、`小伴游戏` 板块，新增“桌面方案”“特效”等板块或标签，不新开一套社区。

**自动检查**

- manifest 校验、体积、文件类型、重复检测（按内容哈希）。
- HTML 类额外扫描：外部网络请求、动态执行字符串、对宿主的越权消息。命中则进入人工审核队列，不命中也保持 T2，需审核才升级 T1。
- 文本与预览图过敏感词和图片审核（论坛“二期未做”的敏感词需先补，见 M2b）。

**应用与统计**

- 按 §5.4 流程应用。应用次数按“成功导入”计，匿名累计，不关联到用户。
- 内容详情显示“被应用 N 次”，用于排序与创作者反馈。

**派生与复刻**（M3）：发布时可标注来源包，作者页显示“被复刻”次数。

### 6.3 桌面方案（F3，M2）

**是什么**：一份清单，记录“这套桌面由哪些内容组成”。

```text
scheme: { name, preview, items: [ { kind, ref, params? } ] }
  - wallpaper  ref → 壁纸站内容 或 已发布内容包
  - effect     ref + 参数（密度、速度、大小）
  - widgets[]  ref + 位置与尺寸（相对屏幕比例）
  - companion  ref（主题）
```

- 方案本身不含可执行内容，只含引用和参数。
- 桌面端“保存当前桌面为方案”：读取当前壁纸、特效、组件布局，生成清单和截图。该功能依赖 PRD_小伴桌面里的“场景搭配与收藏”（本地），如未实现，先做本地版。
- 复刻：逐项检查是否已有，缺的按 §5.4 下载导入，最后询问是否一键应用整套；任何一项被下架或不可用，提示替代而不是整体失败。
- 多显示器、分辨率差异：布局按比例还原，不保证与原图一致，页面写明。

**验收**：在另一台机器上，从一个含壁纸、特效和两个组件的方案点“复刻”，三次确认内完成，且不静默应用任何内容。

### 6.4 工作流与技能分享（F4，M3）

- 形态：帖子加结构化附件：说明、提示词模板、引用的技能/连接器/专家（以市场的 `命名空间/标识` 引用）。
- “导入到 Agent”：打开桌面端，展示将要安装的技能清单和来源，**技能安装沿用现有审查、哈希锁定、逐次批准流程**，工作流本身不携带脚本。
- 社区帖里的技能若不在市场目录，提示“尚未审核，无法一键安装”，用户可去市场申请收录。

### 6.5 悬赏与挑战（F5，M3）

- **需求悬赏**：复用论坛“资源求助”（0–1000 分悬赏、采纳、到期退款），新增分类“我想要一个……”，需求方描述想要的组件、特效或方案，创作者交付内容包帖并被采纳后获得积分。
- **主题挑战**：官方每周发主题帖；投稿为带挑战标签的内容包帖；投票用点赞；截止后站方结算并发放积分、精选置顶。
- 奖励机制尚未确定。首版（含悬赏和挑战）只沿用现有积分流水，不与现金或有价值的权益挂钩；等机制设计好、并有防刷分方案后再开放兑换。

### 6.6 账号与云端沉淀（F6，M3）

| 对象 | 是否同步 | 说明 |
| --- | --- | --- |
| 桌面方案 | 是（用户开启） | 换机恢复，手机端可查看、一键“发到电脑” |
| 自己发布的内容包 | 是（已发布即在云端） | 作品页即备份 |
| 收藏（内容、项目） | 是 | 手机与桌面共享 |
| 壁纸/设置/小游戏存档 | 否（首版） | 保持本地优先，后续单独评估 |
| Agent 记忆、资料库 | **否** | 隐私敏感，且本地库明确不自动上传；若要同步需另立项并默认端到端加密 |

- 所有同步为**用户主动开启**，默认关闭，设置页写明同步哪些、存在哪里。
- 不登录也能使用桌面端全部本地功能，不为社区而增加基础功能的账号门槛。
- **存储**：同步数据先放自有服务器，按用户设容量上限和单文件上限；上线前必须有定期备份和恢复演练，否则“作品页即备份”不成立。换大容量机型之前，先把同步对象限制在方案清单和已发布内容包等小体积数据。云服务器资源有限，按仓库部署规范在本地构建后上传，不在服务器上编译。

### 6.7 桌面端入口（M1 起）

- 控制台新增“社区”页：本周周刊、热门内容包、我的发布、收藏、一键应用入口。
- 首次进入时提示一次，之后不弹窗打扰；周刊更新使用已有的公告/消息机制，不新增常驻弹出。
- 超级小伴可以推荐内容，必须遵守 `agent-proactivity` 的授权、免打扰和每日预算，**默认关闭**。

### 6.8 运营后台

在论坛后台新增：

- 内容包审核队列（自动检查结果、预览、权限说明、通过/驳回/要求修改）。
- 周刊编辑（候选项目池、解读审核、排序、点评、发布）。
- 项目库管理、精选与置顶、挑战管理。
- 漏斗看板（§8），按类型与栏目拆分。

### 6.9 移动端（F7，分阶段）

手机的定位以[路线图](../../client/xiaoban-desktop-wallpaper/docs/assistant-roadmap.md)为准：电脑上小伴的遥控器和收集口，不做第二个完整 Agent。社区相关部分如下：

| 阶段 | 内容 | 前置 |
| --- | --- | --- |
| A | 论坛网页做移动端适配，用现有 `xiaoban-multiplatform` 网页壳打包：浏览周刊、项目页、内容包，发帖回复 | M2b 的 UGC 合规项（只读浏览不需要） |
| B | 原生 Compose 页面：社区信息流、内容包预览与收藏、“发到电脑应用”（经中转）、云端问答（server-ai）、游戏 | 中转服务、F6 收藏同步 |
| C | 遥控电脑上的 Agent、审批推送、分享到小伴 | 路线图第 2 项 |

要点：

- **手机不应用桌面内容包。** 手机上看到壁纸/特效/组件，动作是“发到电脑”；移动端自己的壁纸应用由壁纸 App 负责。
- **游戏类内容包要支持手机端**（已确认）。游戏本身是自包含 HTML，内容基本可复用，但“天然支持”还差一层宿主：手机端要实现与桌面相同的宿主握手协议（存档、成绩）、安全区、沙箱 WebView 和触摸输入。另有几点：
  - 许多游戏默认用键盘，手机没有键盘。建议在 manifest 增加输入方式声明（字段名待定，需同步更新资源包格式文档），手机端只展示声明支持触摸的游戏。
  - `layer: desktop` 的桌面层游戏不适用于手机。
  - 低端安卓的性能、音频自动播放限制需要实测。
  - iOS 对应用内下载并运行第三方 HTML/脚本有审核规则，**上架前需核实**；在核实前，建议 iOS 只放官方内置游戏。
- iOS 与国内安卓商店上架涉及备案和 UGC 审核要求，细节以各商店规定为准，**需在上架前核实，本文不下结论**。

## 7. 安全、合规与治理

| 风险 | 控制 |
| --- | --- |
| 恶意内容包（可执行内容） | 分级放行（§5.2）；HTML 类需审核；沙箱运行；应用前确认；下架后失去一键资格；哈希校验 |
| 项目页中的恶意仓库 | 不执行仓库代码；安全标记；只有已进市场并通过审查的 MCP/技能才有“试用”按钮 |
| README 提示注入 | 仓库文本视为不可信数据，解读流程不执行其中的指令；编辑终审 |
| 刷量与营销号项目 | 异常增长标记、人工复核，不自动上榜 |
| 版权与许可证 | 只摘要和链接，不转载代码与长文；尊重许可证；设置侵权投诉与下架流程（论坛已有） |
| AI 内容误导 | 明确标注“AI 整理”；终审必选；用户可举报错误解读 |
| 生成式 AI 与内容安全合规 | **已决定暂缓**，规模变大后再处理，记为已接受风险。重新评估的触发条件：准备在国内应用商店上架；接入广告、支付或会员；用户规模明显增长；收到投诉或监管提示。在此之前保持“AI 整理、编辑审核”标注和人工终审 |
| UGC 合规 | 举报、屏蔽用户、敏感词、站内通知在开放用户发布（M2b）和手机上架前补齐 |
| 隐私 | 埋点匿名、可关闭、不采集内容；与“本地优先”承诺一致，并在隐私说明披露 |

## 8. 数据与指标

### 8.1 北极星

**周内通过社区内容完成“应用/安装/复刻”的去重用户数**，即“内容→应用”的真实使用量。

### 8.2 漏斗

| 环节 | 指标 |
| --- | --- |
| 看到 | 周刊/内容包/方案的曝光、点开 |
| 行动 | 点“应用/试用/复刻”、确认、成功导入 |
| 留下 | 应用后 7 日仍在使用该类功能 |
| 创作 | 打开创作入口 → 完成创作 → 发布 |
| 社区 | 回复数、收藏数、发布者回访 |
| 全局 | 次日、7 日留存；各模块日活占比 |

### 8.3 埋点原则

- 匿名设备标识，不关联账号；不上传内容、文件名、窗口标题。
- 设置中可一键关闭；默认行为在隐私说明中披露。
- 只记事件与计数，不记明细行为流。

### 8.4 阶段判定

论坛目前没有用户，**没有基线可校准**，所以这里不设数值阈值，只列“要看哪些信号”，由你在每个阶段末回看。

| 阶段 | 要看的信号 | 没有信号时的动作 |
| --- | --- | --- |
| M1 | 周刊发布后：来自搜索和站外分发的独立访客、注册数、项目页回复；桌面端“社区”页的点开率 | 先调整选题和分发再判断；连续数周访客接近零，则不进入 M2b，转为桌面端内的主动推送轻量方案 |
| M2a | 官方内容包的一键应用次数；应用后 7 日是否仍在使用 | 排查应用步骤的摩擦 |
| M2b | 非官方创作者的发布数、被应用次数 | 收紧或延后开放 |
| M3 | 创作→发布转化；审核积压（以你一人能审完为准） | 收紧开放范围 |

## 9. 分期路线

进入下一阶段看信号（§8.4），不按日期自动进入。

| 阶段 | 内容 | 退出条件 |
| --- | --- | --- |

## 12. 风险

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 没有用户：社区还不存在 | 项目页没有回复，UGC 起不来 | 前期只做官方供给的内容；M1 以访问信号为准；用壁纸站和桌面端现有用户做首批触达；必要时转为桌面内主动推送 |
| 审核与发布依赖一人 | 周刊断更、审核积压 | AI 起草、人终审；每期条数以一个人能审完为上限；允许断更一期并预告，不为凑数降低质量 |
| 服务端与桌面端校验不一致 | 发布成功但导入失败，或反之 | 共用测试向量；发布时服务端校验以桌面端规则为准 |
| GitHub 数据源不稳定 | 候选缺失、限频 | M0 实测；保留人工提报通道 |
| 解读成本 | 模型调用费用 | 每项目只生成一次；限制每周候选量；经 server-ai 统一额度 |
| 方案复刻体验差 | 引用内容缺失、布局错位 | 逐项降级提示；先小范围支持，不承诺像素级一致 |
| 范围蔓延 | 团队 2–3 人，同时做装扮、Agent、社区、手机摊不开 | 严格按阶段顺序，每阶段有退出条件和回看点；进入下一阶段看信号，不按日期 |
| 合规不确定 | 上线被限制 | M1 前出结论；手机上架前核实各商店要求 |
