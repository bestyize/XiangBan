# 内容生态与社区：分阶段实施计划

状态：讨论稿。对应 [PRD_内容生态与社区.md](PRD_内容生态与社区.md)（下称“PRD”），把 PRD §9 的路线拆成可开工的工作包。手机应用的界面范围以可点击原型为准（共 30 余张画板，覆盖社区、小伴AI、游戏、我的、模型与额度、资料库、分享）。

本文只排顺序、依赖、交付物和验收。**工期是初估**：按 2–3 人加 AI 编码协作估算，单位是“日历周”，只用来判断先后和量级，开工后每个阶段末回看一次，不当承诺。进入下一阶段看信号（PRD §8.4），不按日期自动进入。

**已定的前提（本版按此排期）**
1. 手机应用 **Android 先行，用 Compose 原生实现**；iOS 后补，现阶段只保证能编译。
2. `server-ai` 由你负责上线，**本计划不把它当阻塞项**，按“联调时已可用”排期。
3. **积分机制先不外露**：新前台和手机应用的界面里不出现积分、悬赏金额；论坛既有的积分后端保留不动。原“悬赏”改为“求助 + 采纳”，不挂积分。
4. 目标是**更快**：见 §4 的压缩手段，总周期比上一版缩短约三分之一。
5. **终审人力已确认**：每周可投入数小时审核，周刊每期按 10 条以内排，终审不是瓶颈。

## 1. 原则

1. **先内容，后工具，最后平台。** 先用周刊和官方内容证明“有人来、有人用”，再开放用户发布，最后做手机原生。
2. **官方内容先行，不依赖论坛用户量。** M2a 的价值要靠官方内容和桌面端存量用户成立。
3. **每个阶段单独可交付、可下线。** 任何一阶段停下，前面的东西仍然是完整产品。
4. **复用现有机制，不另起一套。** 论坛后端、资源包 zip 与 `manifest.json`、`xiaoban://` 深链、关怀提醒、长期目标、市场审查流程、账号中心、`server-ai` 网关。
5. **高风险的放后面。** 用户上传的可运行内容（HTML 类）、云端同步、遥控电脑、实时对话。
6. **新增标识不带品牌词**，改名时不返工（PRD §2.4）。

**累计**：从现在到 M2b 结束约 **10–12 周**（上一版约 20 周），M3 与手机 MC 再约 6–8 周。

### 4.1 压缩手段

1. **工作流并行**：桌面端（D）和论坛后端（B）互不依赖，M1 第 2 周就可以开始 M2a；手机端 MA 直接加载新前台，不等原生。
2. **只做必须的**：先复制链接和海报，再接微信、QQ、微博；先 `effect`、`scheme`，再其他类型；先周刊再项目结构化。
3. **复用而不是新建**：周刊用 `forum-post-studio`，内容包用现有 zip 与 `manifest.json`，积分后端不动，模型与额度对齐桌面端已有逻辑。
4. **让 AI 写重复件**：列表页、表单页、迁移、接口样板、单元测试都由 AI 起草，人只审安全相关和协议相关的代码。
5. **瓶颈不在编码**：真正限制速度的是（a）周刊的内容节奏——每周一期，M1 的“连续 4 期”是硬下限（终审时间已确认够用，卡的是采集和解读的节奏），（b）深链和一键应用要真机验证，（c）M2b 起用户内容的审核人力（周刊终审和用户内容审核共用你的时间，M2b 前要重新核算）。这些**不能靠加快编码来压缩**。若想再快一点，可以把退出条件从“连续 4 期”改成“连续 3 期”。

手机应用的拆分（MA / MB / MC）在 §6 单独展开，**MA 在 M1 内就做，不等到 M3**。

## 6. 手机应用分步（MA / MB / MC）

手机应用是新工程，**不并入壁纸 App**。**Android 先行，Compose 原生实现**；iOS 工程保留，暂不投入。拆成三步，每步可上架。

| 步骤 | 对应阶段 | 范围 | 前置 |
| --- | --- | --- | --- |
| **MA 网页壳** | M1 内（第 3–4 周） | 加载新前台，只读浏览；复制链接；跳转登录（1–2 周） | 前台改版第一版 |
| **MB 原生社区 + 小伴AI** | 与 M2a / M2b 并行（约 8 周） | 底栏五格；原生社区（信息流、详情、搜索、发帖）；小伴AI 首页与对话页；**模型与额度**（小伴AI 列表、兑换、自有服务）；**资料库**（我的文档、收藏，本机）；分享面板与海报；我的、设置 | `server-ai` 可用（你上线）；MA 已上线；M2b 的合规项（发帖回复需要） |
| **MC 能力补全** | M3 内（约 6 周） | 游戏试玩（独立沙箱域名）与排行榜；在线创作；实时对话；联网搜索；拍照提问；“我的电脑”配对与遥控 | 实时网关部署；沙箱域名；Agent 遥控方案 |

**MB 的拆分建议**（每项独立可测）

1. 工程骨架与设计规范变量（颜色、字号、圆角、间距、底栏胶囊、顶部一行）。
2. 账号登录与我的页。
3. 社区信息流与详情（先读后写）。
4. 小伴AI 对话页（文字问答，走 `server-ai` 的响应协议，流式显示）；Android 用 Compose 实现。
5. 模型与额度（档位列表、兑换码、思考强度；自有服务的密钥只存本机）。
6. 资料库（本机存储；发给小伴AI 前明确提示“将发送到云端”）。
7. 发布与发帖（等 M2b 合规项）。
8. 分享（复制链接、海报、系统分享；各平台 SDK 另排）。

## 9. 风险与应对

| 风险 | 应对 |
| --- | --- |
| 范围蔓延（装扮、Agent、社区、手机同时铺开） | 严格按阶段顺序；每阶段末回看；MB 前不开 MC 的任何内容 |
| 周刊靠一个人终审，断更 | 每周数小时终审已确认；先固定每周一期、10 条以内；M2b 开放后周刊与用户内容审核共用时间，要重新核算；断更两周降级为“精选合集” |
| 论坛没有用户，开放过早没人用 | M2a 不依赖论坛用户量；M2b 看信号，没有信号不开放 |
| 主机带宽（12 Mbps）被图片或下载占满 | 封面、预览图、zip 全部放资源机（200 Mbps）；主机只跑接口；下载限流；资源机带宽到 70% 告警 |
| 压缩周期后审核与真机验证跟不上 | 瓶颈是人，不是代码：M2b 前先把审核清单和真机验证用例备好；宁可延后开放，不压缩安全检查 |
| 用户上传内容引入安全问题 | T2 只开放纯数据类；HTML 类须审核；游戏只在独立沙箱运行；导入从不自动应用 |
| `server-ai` 上线时间不确定 | 你负责上线；MA 不依赖它；MB 的对话页可先用假数据开发 |
| 分享 SDK 审核周期长 | 首版以复制链接、海报、系统分享为主 |
| 与桌面端、壁纸 App 的数据模型不一致 | 新增表追加不改旧表；数据目录不迁移；跨端的 `manifest.json` 版本显式 |
