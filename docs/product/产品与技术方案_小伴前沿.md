# 小伴前沿：产品与技术方案

状态：首期方案及实施补充，部分已实现。日期：2026-11-02。服务归属超级小伴论坛 `services/server-forum`。实际实现和部署状态以该服务 README 及代码为准。

2026-11-02 实施补充：栏目、图片隔离及人工审核链路已实现；根据后续自动采编需求，增加独立 sidecar 和可显式授权的 `frontier` 自动发布通道。采集令牌默认仍只写草稿，自动发布记录使用机器操作身份。当前实现、已接入栏目及限制见 `services/server-forum/editorial/README.md`；下文的“首期不自动发布”保留为最初阶段边界，不代表后续已授权阶段的实现状态。所有栏目各20篇的运营目标仍未完成。

## 1. 产品目标

在小伴社区提供科技媒体式的 AI 资讯和解读：由 AI 协助发现热点、查找和整理资料、撰写图文，经编辑核实后发布。面向对 AI 感兴趣的普通用户、开发者与创作者，帮助他们快速了解发生了什么、为什么重要、可以怎样使用及目前有哪些限制。栏目风格借鉴科技媒体的可读性与选题方式，建立自己的品牌和表达，不照搬具体媒体的稿件、标题或视觉。

首期建议每天收集候选，编辑选择后生成 1～3 篇待审稿；这是运营目标而非必须填满的配额，没有合适选题可以不发。覆盖 AI 新产品与模型、重要技术和论文、工具体验；重要事实必须有可核验出处。

不纳入首期：自动公开发布、未经核实的全网热点榜、自动抓取和转载付费或受限全文、对话式新闻编辑器、复杂推荐算法、跨平台自动分发，以及虚构体验或测试结果。

## 2. 与现有入口共存

| 入口 | 职责 | 关联方式 |
| --- | --- | --- |
| 发现首页 | 汇聚值得浏览的社区内容 | 新增「小伴前沿」精选区，展示 2～3 篇已发布文章和「查看全部」；空状态隐藏或显示可解释的占位，不影响其他模块。 |
| 日报 | 简短资讯聚合 | 保留原列表、详情和评论；有相关文章时显示「阅读完整解读」，指向前沿文章。关联缺失或文章下架时不展示链接。 |
| 讨论 | 社区用户交流和发帖 | 文章保留自身评论；用户如需深入交流，可主动发帖并粘贴文章链接。首期不自动创建讨论帖或同步评论。 |
| 资源 | 工具、资料与作品 | 文章可链接现有资源，资源数据仍由原功能管理；无效或下架链接不应被包装成可用资源。 |
| 小伴前沿 | 站方图文报道与解读 | 独立文章列表和详情，统一正文、来源和评论；日报只引用，不复制完整文章。 |

手机网页先通过发现首页进入，不增加底栏；PC 在侧栏社区相关区域增加入口。具体布局需遵循现有响应式页面。首期覆盖论坛网页；手机原生社区可继续使用原接口，是否新增原生入口及兼容策略单独排期，不宣称自动支持。桌面社区网页随网站更新获得网页入口。

## 3. 读者体验

### 列表与详情

- 列表按发布时间倒序，卡片含封面、标题、摘要、栏目标签、发布时间和编辑身份；支持分页及「全部 / AI 新鲜事 / 热点解读 / 动手体验」筛选。无封面使用统一占位。首期不做个性化推荐。
- 详情含标题、摘要、发布时间、编辑身份、AI 辅助制作说明、封面、Markdown 正文、可点击来源列表及评论。正文适配窄屏、图片有替代文字；来源时间、采集时间和站内发布时间分别表达，未知不猜测。
- 每篇文章一个稳定 URL（建议 `/frontier/{key}`）和一个评论区。分享、SEO 标题/摘要、规范链接及 sitemap 以文章自身为准；服务端 SEO 能否复用现有渲染须在实现时核实。非公开文章不进入公开 API、SEO、sitemap 或首页。
- 日报与文章可多对多关联；关联仅保存在日报侧或独立关系表，不在两边维护两套正文。文章更新后所有入口看到同一版本。删除、撤回、未到发布时间时链接不可见；旧 URL 给出清晰的不可用状态，避免泄露草稿。

### 文章格式

默认结构：简短导语、核心事实、背景和影响、适用场景与限制、来源。体验类文章必须说明实际使用条件；未亲测就明确写「基于官方资料」，不能写成亲身体验。标题可有吸引力，但不夸大、不用无依据的绝对化结论。文章内嵌必要引用，文末列出原始来源及访问时间；信息不足则不做确定性结论。

## 4. 内容生产与运营

1. **发现**：沿用现有官方 RSS 候选，并逐步配置经过评估的官方博客、研究机构、论文和产品发布源。记录 URL、标题、来源、原始发布时间（可空）、采集时间及采集批次。首期只自动采集允许获取的元数据；来源规则和授权不允许时不抓正文。热点判定先基于来源、时间和编辑判断，不把来源数量伪装成全网热度。
2. **去重和选题**：以规范化 URL、来源标识及标题相似性聚合候选；同一事件的多个来源可以合并并保留出处。自动去重只作提示，编辑可合并、忽略或手动创建选题；已报道的更新须说明新增事实。展示候选原因、来源、时间和相似稿件。
3. **研究**：优先官方公告、论文和产品文档，多来源交叉核对关键事实。记录来源链接、可供核对的事实及其时间；取材不足或互相矛盾时进入待补证，不生成可发布结论。尊重站点访问规则、授权和版权，少量必要引用应有明确出处，不存储或转载不必要的受限全文。
4. **成稿**：编辑确认选题后，AI 生成标题备选、摘要、结构化正文、来源清单及配图建议。输出事实与来源的对应关系、尚待核实项和生成模型/时间，供后台审阅，不向读者展示内部提示词。生成失败保留既有人工稿和资料，可单步重试。
5. **视觉**：每篇建议一张原创封面，必要时补充示意图或图表；可无图发布，不用图片数量凑配额。AI 生成图标为示意，不伪装真实人物、产品界面或现场；真实截图、Logo 和第三方图片须有适当使用依据及来源。可由编辑替换、删除和填写替代文字。
6. **审核与发布**：编辑检查事实、来源、标题、版权、图片、格式及敏感内容，必要时修改；只有人工终审后的固定版本能立即或定时发布。标注「AI 辅助创作，编辑审核」；未审核、证据不足或生成失败均不得发布。发布后发现错误可更正并注明时间与内容；严重问题可撤回。

后台建议提供候选箱、选题详情、来源与证据、生成任务、图片管理、稿件预览、待审与发布记录。角色首期沿用现有管理员权限；采集/生成凭据仅写草稿，审核和发布仍由管理员执行。所有来源、图片权利依据和更正记录可被管理员追溯。

## 5. 现状与技术决策

目前论坛已有官方 RSS 元数据采集、`news` 发现页草稿和人工发布；`News` 已含封面、摘要、Markdown 正文、来源和时间字段。现有发现页工作流具备版本冲突检查、审核、定时发布、审计及范围受限的采集令牌；日报详情有独立评论。站方图文编辑器另有帖子草稿与发布，属于不同内容路径。当前官方 RSS 只取固定来源的元数据，不等于已有自动写稿、生成图片或完整热点搜索。

**首期推荐新增 `frontier` 发现内容类型，复用发现页的草稿、审核、定时发布和 Markdown 能力。** 保留现有 `news` 的读写和日报接口语义，避免新增文章进入日报列表、影响旧客户端；为前沿文章新增专门列表/详情和评论路由。两者以明确的关联记录连接。实现前确认 `discover` 的校验、权限白名单、发布事务、管理台与 API 都支持新类型；这是规划，不能假设加枚举即可完成。

评论可抽出日报现有校验和操作逻辑供两类内容复用；目前评论表按 `news_key` 组织，不能直接把不同类型的同名 key 当成同一篇。建议新增按 `(kind, key)` 隔离的通用评论存储，或为前沿使用独立表并复用业务代码；旧日报表与接口先保持兼容。具体迁移需评估现有数据和测试，禁止把历史评论静默搬走或跨文章串联。

## 6. 数据与接口设计

以下为实现建议，命名和字段需以开发时的代码评审为准：

- **前沿文章**：使用 `discover_items(kind='frontier', key, data, status, published_at, …)` 和对应草稿。`data` 至少包括标题、摘要、正文、封面资产引用、分类、编辑署名、来源数组、AI 辅助标识及更正记录。区分原始来源时间、采集时间和站内发布时间；正文、来源和图片引用在服务端校验并限制大小。
- **候选与事件**：独立候选记录保存来源 ID、原始和规范 URL、标题、时间、批次、状态、事件聚合关系；来源 ID + 来源内唯一标识做唯一约束，URL 规范化仅用于去重提示，不假设不同 URL 必然是同一事件。
- **研究资料**：保存来源元数据、引用位置或可核验事实、访问时间、权利说明和编辑备注；保留必要证据，避免长期保存不必要的第三方全文。
- **文章关系**：独立关联表保存日报 key 与前沿 key，唯一约束防重；查询时验证两侧已发布且已到发布时间。无关联也可独立发布。
- **任务与资产**：生成任务记录阶段、状态、尝试次数、模型、费用/用量（若供应商返回）、错误摘要、生成版本及人工修改基线；图片记录存储位置、用途、来源或生成方式、权利备注、alt 和引用状态。密钥、完整提示及不必要的第三方正文不写普通日志。
- **公开 API**：建议增加 `GET /api/discover/frontier`、`GET /api/discover/frontier/{key}` 及其评论接口；关联信息由日报详情或独立只读接口返回。全部只返回可公开内容。已有 `/api/discover/daily*` 行为保持兼容。
- **管理 API**：扩展现有 `/api/admin/discover-workflow` 处理 `frontier` 草稿；候选、生成、素材与关联提供单独受控管理接口。服务端再次校验类型、权限、版本、发布状态和来源字段，不依赖前端按钮隐藏。

## 7. 调度、模型、图片和部署

- 复用论坛服务内采集与调度基础设施，新增任务默认关闭，后台可手动运行并配置频率、来源、数量和预算上限；不使用 GitHub Actions 自动触发。生产默认时区为北京时间，记录实际执行时间。多实例采用数据库租约/锁和幂等键，避免重复采集、重复生成和发布；超时、重启及失败重试有上限，保留上一次有效内容。
- 文本生成通过服务端可配置模型适配器接入；先核实 `server-ai` 是否支持站方机器身份、独立额度与所需接口，未确认前不假定能直接复用用户额度。否则采用独立受控的服务端供应商配置。生成任务设调用次数、字数、超时和费用上限，密钥不下发前端、不写仓库，按既有加密与审计机制管理。
- 图片生成是可插拔能力：实现前确认可用的图像服务、费用、生成内容授权和存储容量；不可用时允许编辑上传有权使用的图片或无封面发布。草稿图片需鉴权预览，发布后才公开；引用、替换、撤稿、清理、备份需覆盖草稿及已发布版本，不能直接假设普通正文图片的清理逻辑支持新类型。
- 只采集配置允许的来源，对外请求限制协议、目标地址、重定向、响应大小和超时，防止服务端请求内网和资源耗尽；不执行来源内容。Markdown 沿用安全渲染，图片验证真实类型。生产资源、密钥、存储和外网访问需要部署前单独核实；云服务器使用本地构建产物部署，不在云端大型编译。

## 8. 状态与并发

候选状态建议为「新发现 → 已选题 / 已忽略 → 已关联稿件」。生成任务为「排队 → 运行 → 成功 / 失败 / 取消」，任务状态不等于发布状态。文章继续使用现有发现页草稿、审核、定时和发布流程：生成结果只创建或更新草稿；编辑修改后旧审核失效；审核绑定具体 revision；到期发布前复核 revision、线上基线、来源和资源状态。并发编辑或生成回写发生冲突时保留人工版本并提示合并，不覆盖。

撤回或删除应隐藏公开详情、关联入口和 SEO；评论如何保留、恢复或删除遵循现有社区管理与数据保留规则。定时任务失败提供后台可见的原因和重试入口，不能静默改成已发布。审计记录操作者、动作、对象、版本和时间，不记录密钥。

## 9. 分阶段实施与验收

### M0：人工试运营

使用现有草稿和图文工具制作少量样稿，检验选题、引文、图片权利、阅读体验和人工审核工作量。此阶段不宣称已有新栏目或自动化能力。确认样稿质量、运营人员和模型/图片服务后进入开发。

### M1：栏目与人工审核发布

新增 `frontier` 内容类型、公开列表/详情、评论、首页专区、PC 入口、日报关联和后台编辑/审核；支持手工录入来源与上传图片，复用现有版本与定时发布机制。验收：访客能从首页进入并阅读；旧日报、旧评论和原接口不变；草稿及未来发布时间内容不可见；关联目标下架后入口消失；编辑冲突不丢内容；窄屏与 SEO/分享正常。

### M2：候选与 AI 辅助生产

接入配置化来源、候选去重、资料记录、按选题触发成稿及可选封面生成。验收：来源和不确定项可追溯；自动任务只能写草稿；失败或重复执行不覆盖人工修改、不重复创建发布内容；模型/图片不可用时可手工完成；限额与错误可见。

### M3：运营优化

根据实际阅读、来源质量和审核负担优化候选排序、栏目分类与关联；再评估原生手机入口和更高级自动化。自动发布不在本方案首期范围，必须另行明确质量标准和授权。

## 10. 测试与观察

- 后端针对内容类型隔离、权限、来源和 URL 校验、版本冲突、定时审核、关联可见性、评论隔离、重试幂等及失败恢复编写测试；数据库测试使用隔离 `TEST_DATABASE_URL`。验证命令参考 `services/server-forum/README.md`，并对新增模块运行针对性测试。
- 前端验证首页空态、列表分页、移动端排版、详情与评论、审核预览、关联失效及无图降级；执行论坛网页相关测试和构建。确认旧日报链接及既有客户端解析兼容。
- 每周查看候选到选题转化率、审核退回原因、发布篇数、阅读与评论、来源可用性、生成失败率及成本；首月主要看事实错误/更正、人工审核耗时和读者反馈，不用浏览量作为唯一目标。沿用已有匿名聚合统计与隐私设置，不新增个人阅读轨迹。

## 11. 待确认事项

栏目名称与编辑署名；首批可信来源及使用权限；实际文本和图片服务、预算与调用凭据；谁负责选题和终审；封面视觉规范；首期是否需要原生手机入口。这些选择不改变「人工终审后发布」的首期边界，未确定时可先使用占位名称、人工选题、无图降级及网页入口。
