# 小伴成为办公 Agent 与个人助手：方向与排序

整理于 2026-10-23，供后续会话接着做。结论：小伴的“手”（文件、命令、网页、技能市场、MCP、电脑操作）和“记性”（目标、定时任务、提醒、经确认的记忆、资料库）已经比较齐，最缺的是**接入工作真正发生的地方**（日历、消息、云文档）、**不用开口也在推进事情**，以及一个**手机上的入口**。按用户安排，先做资料库检索和手机 App，飞书往后放。

## 总排序

| 顺序 | 方向 | 一句话目标 | 前置 |
| --- | --- | --- | --- |
| 0 | 质量门槛 | main 测试全绿，合并前跑全量测试 | 已完成 |
| 1 | 资料库检索 | 回答时自动从资料库找依据并标出处 | 无 |
| 2 | 手机 App（Android，Compose） | 先做电脑上小伴的遥控器、收集口和纯聊天；长期在手机上跑 Agent 内核，能创作小组件包、小游戏包 | 中转服务 |
| 2b | 小伴驱动外部编程 Agent（Claude Code、Codex） | 在小伴里开会话让 Claude Code / Codex 干活，看进度、批权限；配合手机 App 就能像 Happy 那样在手机上遥控 | 2 的中转服务与审批推送；各 Agent 的无界面接口（先核实） |
| 3 | 主动性：会议纪要、待办追踪、每日简报 | 每天打开小伴的理由 | 简报里的日程需要方向 4，可先做不依赖日历的部分 |
| 4 | 连接飞书（含机器人） | 小伴能读写我的飞书日历、消息、云文档 | 2 抽出的消息通道层可复用 |
| 5 | 更多消息通道：企业微信、QQ | 覆盖用企业微信办公和偏个人场景的用户 | 消息通道层 |
| 6 | 交付质量 | Office 产出能直接交差；融入正在用的软件 | 无，穿插进行 |

调整记录（2026-10-23）：飞书往后放；手机 App 提前，先做 Android，用 Compose 写，将来 iOS 以它为底座（Kotlin Multiplatform + Compose Multiplatform）。

调整记录（2026-10-28）：手机端定位改为分三步走——先“遥控桌面端 + 纯聊天”，长期目标是手机上有自己的 Agent 内核和工具，能在手机上创作小组件包、小游戏包等内容包。详见下节“手机端的分期”。

个人微信：**不做**。没有找到官方机器人接口，现有方案依赖非官方协议或模拟操作窗口，有封号风险、可能违反平台协议、维护成本高。

## 0. 质量门槛（已完成）

- **原因**：PR #98 把桌面工具改成按需加载（模型先 `tool_load` / `tool_search` 才能调用，否则被拦下），7 个测试仍直接调用桌面工具。按设计意图改测试：先加载再调用；工具清单测试改为检查“每轮都带的工具”和“目录里列出的按需工具”两部分。
- **顺带修的实现问题**：按需工具目录限 6000 字节，中文描述每字 3 字节，电脑控制修复、社区分享、无障碍授权 5 个工具被挤出目录，模型不知道它们存在。现在放不下摘要的工具仍列出名字（`libs/agent-kernel/src/discovery.rs`）。另修了 PR #99 `network.rs` 的编译错误。
- **之后**：整理一套固定的办公任务评测集（整理文件、写周报、做表格、回邮件等），每次改 agent 都跑一遍对比。约定合并前本地跑全量（GitHub Actions 只能手动触发，不能靠 CI 拦）。

## 1. 资料库检索（让小伴懂你的工作）

- **现状**：资料库已上线（我的文档 / 云文档 / 收藏 / 记忆，见 `docs/design-specs/library.md`）。文档导入后已在后台抽取文字（`src-tauri/src/data_library.rs` 的 `read_text`），但目前只能手动「用这份资料提问」作为附件带上。
- **目标**：回答时自动检索资料库相关段落，标注出处（“依据《年度预算》第 4 页”）。
- **方案**：本地推理引擎 `tools/xiaoban-infer` 加一个文本向量能力（引擎当初改成通用名就是为此，新增能力是加一个模块并在 `start` 登记）；本机建索引，资料不上传；给 agent 加一个只读的资料库检索工具（同 `experience_recall` 的做法，受「让小伴记住我」之外的独立开关控制）；回答下显示引用来源，可点开定位。记忆与资料库联动（“那份周报模板”能找到具体文件）。
- **完成标准**：导入一份 PDF 后，不手动附件，问其中内容能答对并给出出处。

## 2b. 小伴驱动外部编程 Agent（2026-10-28 提出）

目标：**小伴是唯一的对话入口**。用户在手机或电脑上，用打字、语音、实时对话（现有的伪实时，不新做实时网关）跟小伴说话；小伴自己判断是亲手做、还是交给 Claude Code / Codex 去做，做的过程中用户随时能问进度、追加要求、批权限。参照 Happy 的遥控体验，但会话由小伴拉起，不要求用户改用另一个启动命令。

```
用户（手机 / 电脑；文字、语音、实时对话）
        │
     小伴（对话、记忆、资料库、提醒 + 调度）
   ┌────┼──────────────┐
 自己做   委派 Claude Code   委派 Codex     ← 外部 Agent 是小伴的“工具”，不是并列入口
```

- **委派作为小伴内核的工具**：新增 `agent_delegate`（选 Agent、工作目录、任务描述）、`agent_status`（列出并查看进度）、`agent_reply`（回答它的提问或追加指令）、`agent_approve`（转交权限请求的决定）、`agent_cancel`。小伴按对话判断用哪个；用户也可以明说“让 Codex 去做”。
- **任务是异步的**：外部 Agent 一跑就是几分钟到几十分钟。小伴发起后立即回话，进度和结果以通知形式主动汇报（文字，语音场景下可朗读一句摘要）；用户中途问“做到哪了”，小伴读取该会话的最新事件回答。
- **语音场景的约束**：语音识别可能听错，所以语音触发的委派要先复述任务和目录再确认（可一句话确认）；权限请求只朗读摘要，批准以屏幕上的明确操作或一句明确的口令为准，**高危操作（删除、推送、联网安装、写工作目录之外）不接受纯语音批准**。
- **手机与电脑**：对话的“大脑”在电脑上的小伴（有外部 Agent 和本机工具）。手机在线时：手机的文字/语音经中转发到电脑小伴，回复和通知回到手机。电脑离线时：手机退回云端纯聊天，并明说“电脑不在线，不能让 Claude / Codex 干活”，不假装能做。

- **做法**：小伴把外部 Agent 作为子进程拉起（无界面模式，结构化事件流输出），解析事件在聊天界面里显示（文字、工具调用、改动的文件、权限请求），用户的回复和审批再写回子进程。每个外部会话记录工作目录、会话编号，支持恢复。
- **接入方式（开工前先核实各 Agent 当前版本的接口，不凭记忆写）**：
  - Claude Code：无界面模式的流式 JSON 输入输出，权限请求走其“权限提示工具”机制，会话可按编号恢复。
  - Codex：JSON 事件输出的非交互模式，或其面向编辑器集成的服务模式。
  - 若 Agent Client Protocol（ACP）的适配器足够成熟，优先用它做统一接口，只写一层适配；否则每个 Agent 写一个适配器，放在同一个 trait 后面。
- **与原生 Claude Code / Codex 并存（2026-10-28 补充）**：目标是工程和对话两边通用——在小伴里开的会话，回到终端或桌面版能接着用，用户自己在终端里开的会话，小伴也能看到并接手。小伴只做“外挂的语音助手”，不另起一套会话。分三层，由浅到深，每层单独可用：
  1. **观察层（不改变用户习惯）**：小伴帮用户在 Claude Code 的设置里装 hooks（任务结束、等待权限、需要输入时通知本机小伴），在 Codex 的配置里装 notify 回调，并读取它们落盘的会话记录（Claude Code 在 `~/.claude/projects/` 下，Codex 在 `~/.codex/sessions/` 下，均为 JSONL，具体路径与格式开工前核实）。效果：用户照常在终端或桌面版里用，小伴能播报“做完了/在等你批准”，能回答“它现在在做什么”。这层只读，不能往正在运行的终端里输入。
  2. **接续层（会话共用）**：某个会话当前没有进程在跑时，小伴用官方二进制的无界面模式按会话编号恢复它，把用户的语音指令作为下一轮输入；结果写回同一份会话记录，所以之后回到终端 `resume` 就能接上，反过来在终端里聊了几轮，小伴下次也接得上。同一会话同一时刻只允许一个驱动方：发现有进程在占用，小伴告知而不强行写入。
  3. **托管层（完全可控）**：用户通过小伴（或一个很薄的启动垫片，如 `xb claude`）启动，进程由小伴持有，可实时输入、处理权限、中断。这是体验最好的一层，也是对上游界面变化最敏感的一层。
  4. **界面层（针对桌面版应用，2026-10-28 补充）**：Claude 桌面版、ChatGPT 桌面版的对话没有可恢复的命令行接口，要让用户对悬浮条说的话“直接出现在它们的对话页里”，只能由小伴操作那个应用的界面：把话转成文字，显示在悬浮条上让用户确认，再切到目标应用，聚焦输入框，粘贴并回车。基础已有：悬浮条（`float_assistant`）和语音识别。**不用内置的桌面控制引擎（`computer-use`）**：它靠看屏幕图像、再由模型决定点哪里，每一步要几秒，且结果不确定；这里要的是毫秒级、可预测的脚本式操作，**全程不截图、不调用模型**，直接调系统接口。做法与限制：
     - 按由稳到脆的顺序尝试，前一种成功就不往下走：①目标应用自带的全局快捷键（如快速输入窗口，开工前核实各应用是否提供及默认键位），触发后直接粘贴；②用系统无障碍接口（Windows UI Automation，macOS Accessibility）按进程名找到窗口并聚焦输入框，写入文字；③只激活窗口，不定位输入框，直接粘贴并回车（依赖应用打开时输入框已有焦点）。这些都是本机接口调用，单次几十毫秒；
     - 通过粘贴输入，粘贴前后保存、恢复用户的剪贴板，避免逐字模拟按键造成的中文输入法问题和延迟；
     - Electron 类应用的无障碍树默认可能不完整（Windows 需要有辅助技术被检测到、macOS 需要打开其增强无障碍开关），开工前逐个应用验证，不行就退回第①或③种；
     - 默认**先上屏、后发送**：文字先进入对方输入框，用户说“发送”或点一下才回车，防止听错或发到错误的窗口；
     - 能确认目标应用在前台且是预期的窗口才输入，否则只提示，不乱发；
     - 读回对方的回复不稳定（无障碍树可能读不到或不完整），也不用截图识别，首版只做“发出去”，回复让用户在应用里看；
     - 对方应用改版会让定位失效，需要为每个应用写适配并做版本回归；macOS 需要无障碍与屏幕录制授权，Windows 上目标应用若以管理员运行则无法操作；
     - 只操作用户自己打开的应用界面，不接触其登录令牌，也不代替用户登录。
     这一层不依赖会话文件，所以对 Claude Code 的桌面版、Codex 桌面版、ChatGPT 桌面版都能用同一套机制，但每个应用要单独适配。
  另外两处深度融合不依赖会话文件：
  - **给它们装“语音工具”**：小伴在本机提供一个 MCP 服务，通过配置装进 Claude Code / Codex，提供“向用户语音提问”“朗读一句话”“发通知”等工具，这样 Agent 做事中途需要问用户时可以直接开口问。
  - **工程层面本来就通用**：它们操作的都是用户磁盘上的工程目录和 git，小伴不额外包装，只负责在对话里记住“这个目录对应哪个会话”。
- **代为安装与配置**：小伴检测本机的 Node、git、Claude Code、Codex 及其版本，缺什么就给出**官方安装命令**，用户确认后在小伴里执行并显示进度；登录由用户在浏览器里完成，小伴只引导，不碰其凭据；可帮配置国内常见的网络环境（代理、镜像源、第三方兼容接口地址）和常用设置；也包含 ChatGPT 桌面版等相关软件的下载引导。检测、安装、升级、卸载都在同一页完成，失败时给出可复制的错误信息。
- **红线**：只拉起用户本机安装的官方二进制；**不读取、不转存、不借用它们的登录令牌，不拿用户的订阅额度去给第三方界面提供服务**；不重新分发它们的程序。这既是上游条款的要求，也避免被封号和被下架。
- **产品形态（待定）**：想做“快速出圈”的话，建议把“语音编程”做成小伴里一个可单独发布的精简入口（托盘常驻、全局热键说话、一个小窗显示会话），复用现有的识别、合成和对话流程，不带壁纸和社区，下载小、首次使用三步内能说出第一句话。同类产品（手机遥控类如 Happy，语音听写类如 Wispr Flow、Superwhisper，Claude Code 自带的语音输入）已存在，差异点要放在：中文识别、整段对话式而不是听写、主动播报进度、权限的口头确认、多工程调度、一键装好环境。上线前逐个核实它们现状。

- **和小伴自己的 Agent 的关系**：小伴内核负责对话、记忆、资料库、提醒和内容包，也可以直接做轻量的活；编程类的重活交给外部 Agent。外部会话的结果由小伴摘要进自己的对话。外部会话完整的过程仍保留在它自己的会话里，可展开查看。
- **委派的授权**：首次对某个目录委派要用户确认并记住；每个外部会话的权限模式（只读、允许改文件、全部询问）在发起时选定，默认最严格；小伴不得自行提升外部会话的权限。
- **安全**：外部 Agent 自带权限体系，小伴只转发它的权限请求，不替用户默认同意；工作目录必须由用户选择；经手机远程发来的指令默认最严格，高危审批在手机上要二次确认；会话日志落在本机，经中转时端到端加密。
- **限制**：拉起的会话才能被接管，已经在别的终端里跑着的会话接不进来（只能按编号恢复新开一个）；用户需自行安装并登录这些 Agent，小伴不代管它们的账号和额度。
- **与手机端的关系**：手机步骤一的“我的电脑”遥控，会话列表里同时显示小伴自己的会话和外部 Agent 会话；审批推送、断线重连、扫码配对共用同一套中转协议。
- **完成标准**：
  1. 对着小伴说（或打字）“用 Claude Code 在这个项目里把某个测试修好”，小伴复述任务并确认后开始；
  2. 过程中问“做到哪了”，小伴能答出当前在做什么；
  3. 它请求权限时，电脑和手机同时收到确认，批准后继续；
  4. 做完后小伴主动汇报结果，并在语音场景朗读一句摘要；
  5. 关闭小伴再打开可恢复该会话；
  6. 电脑离线时手机明确告知不能委派。

## 2. 手机 App（Android，Compose）

- **定位（分三步）**：第一步是电脑上小伴的**遥控器和收集口**，加不依赖电脑的云端纯聊天；第二步起在手机上带 Agent 内核和工具（见下“手机端的分期”）。原先“不在手机上再做一个完整 agent”的约束取消，但按分期推进，不在第一步里提前做。
- **技术**：Android 先行，界面用 Jetpack Compose；业务和界面尽量写在 Kotlin Multiplatform 的共享模块里、界面用 Compose Multiplatform，将来 iOS 以它为底座（iOS 只补平台相关的推送、分享、相机等）。平台相关代码用 `expect/actual` 隔开，别让 Android SDK 漏进共享模块。
- **只做四件事**：与电脑上的小伴对话（经中转服务，可看进度）；审批卡片与推送（动文件、发消息、跑命令前推到手机确认）；「分享到小伴」与拍照存进资料库；电脑离线时用云端模型简单问答并说明离线。
- **中转服务**：手机与电脑通常连不上，建议放在 server-ai（账号、配额、云端模型都在那里）。电脑端主动长连接到中转，不需要电脑有公网地址。远程来的任务默认最严格权限，每条远程指令留记录，只认本人账号。这一层做成通用的「消息通道」，以后飞书机器人、企业微信、QQ 复用。
- **代价**：国内推送要接各厂商通道；上架一般需要 APP 备案，很多商店还要软件著作权（以各商店要求为准）；多一个客户端的维护成本。
- **起点**：`client/xiaoban-multiplatform`（Kotlin Multiplatform + Compose，目前只是网站套壳，统一账号现成）；`client/xiaoban-mobile-wallpaper` 有安卓机型适配经验（例如小米）。
- **开工前**：先出设计稿（对话、审批卡片、分享收集、离线四个界面），再定中转协议；确认 `xiaoban-multiplatform` 现有工程结构能否直接承载，还是另起模块。
- **完成标准**：手机上发一句话，电脑上的小伴开会话去做，手机能看到进度；需要确认的操作推到手机，点同意后电脑继续；从相册分享一张图进小伴，出现在资料库里。

### 手机端的分期（2026-10-28 定）

| 步骤 | 内容 | 说明 |
| --- | --- | --- |
| 一 | **纯聊天 + 遥控桌面端** | 手机上与云端模型对话（server-ai，流式）；“我的电脑”配对后，把任务经中转发给电脑上的小伴、看进度、处理审批推送。手机上没有任何本地工具。 |
| 二 | **手机上的轻量 Agent 内核** | 把现有 Rust 内核（agent-kernel，已验证能为 Android 目标编译）通过 UniFFI/JNI 嵌进应用，工具用 Kotlin 在手机侧实现：资料库、网页获取、内容包读写、定时与提醒等；不引入 shell、任意文件系统、桌面控制。网络请求走 rustls，不依赖系统 OpenSSL。 |
| 三 | **在手机上创作内容包** | 在步骤二的基础上加创作工具：生成小组件包（widget）、小游戏包（game）等，在手机上预览，发布到社区。创作产物遵守社区的体积上限、清单格式和审核流程；手机上运行用户创作的网页内容必须放进沙箱（独立域名或受限 WebView，不给应用桥接）。 |

约束：
- 步骤二、三的权限比桌面更严：工具逐个开放，默认需要用户确认；手机上不执行来自远程的任意命令。
- 内核共用同一份 Rust 代码，不在 Kotlin 里重写；手机特有的部分只写工具和宿主。
- 步骤三依赖社区的 widget/game 内容包规范与沙箱域名（实施计划 MC），所以排在它们之后。

## 3. 主动性（每天打开小伴的理由）

- **会议纪要**：已有本地语音识别（SenseVoice + 判停）。加录音、按说话人分段，自动出纪要和待办，全程本机完成。
- **每日简报**：早上一张卡片：今天的会（需方向 4，之前先不显示日程）、待回复的消息、到期的事、昨天没做完的任务。
- **待办追踪**：对话和会议里“我下周三前给你”自动记下，到时提醒（已有提醒和定时任务机制）。
- **例行事项**：把底层定时任务做成用户能看见、能编辑的入口，例如每周五自动起草周报。

## 4. 连接飞书（含机器人）

- **为什么**：没有日历、消息、云文档，小伴只是聪明的聊天窗口；接上之后才是能替你办事的助理。飞书一家就能拿到三样，开放接口最完整。
- **已查明的事实**
  - 个人可以做：注册飞书后自己建组织，自己是管理员，在组织里建「企业自建应用」、发布都不需审核（已用 lark-cli 实测，未要求提交任何材料）。
  - 自建应用只在所属组织有效。读公司组织的数据，要在公司组织里建应用并经管理员审批。
  - 让任何用户扫码即用，需要「商店应用」，按通行做法要企业主体上架（未查到官方原文，需在开放平台发布页核实）。
  - 飞书官方 [lark-cli](https://github.com/larksuite/cli)（MIT）：`config init --new` 一键建应用拿凭证；`auth login` 走 OAuth，支持 `--no-wait` 先返回链接、`--device-code` 之后续上；输出默认 JSON；`--as user / --as bot` 切换身份；自带 200+ 命令和 Agent 技能。安装：npm（`npx @larksuite/cli@latest install`）或源码（Go 1.23+）。
  - 另有官方 OpenAPI MCP（`@larksuiteoapi/lark-mcp`），支持用户身份；自动续期需在 scope 里含 `offline_access`。
- **方案：用户自带应用，不依赖上架**
  1. 像本地推理引擎一样按需下载 lark-cli（固定版本、校验文件）。
  2. 资料库「云文档」→「连接账号」做成「连接飞书」：在小伴里分步引导，跑建应用和授权，授权链接以二维码显示在小伴里。
  3. 把 lark-cli 自带技能装进小伴技能目录，小伴即可查日历、发消息、读写云文档；资料库里的飞书链接变成「小伴可读取」。
  4. 写操作（发消息、改文档）照常走小伴的确认流程。
  5. 代码按“应用凭证可替换”设计：以后有商店应用，换凭证即可让其他用户扫码直用。
- **机器人（手机入口）**：同一个应用带机器人身份。手机飞书里给机器人发消息 → 电脑上的小伴开一个会话去做 → 结果与提醒推回。用长连接收消息，**不需要公网服务器**。
  - 安全：只认本人账号；远程来的任务默认最严格权限，动文件、发消息、跑命令前推确认卡片到手机；每条远程指令留记录；电脑离线时直接回“小伴不在线”。
  - 复用方向 2 的「消息通道」层。
- **开工前要查清**：lark-cli 凭证存在哪、能否放进小伴数据目录；`--recommend` 申请哪些 scope；公司账号（非管理员）建应用是否要审批；机器人长连接收消息的具体方式。
- **需要用户提供**：自己飞书组织里的测试应用（App ID / Secret），用于联调。
- **完成标准**：在小伴里点「连接飞书」→ 浏览器确认 → 扫码授权；问“我明天有哪些会”能答对；能把一段回答写成飞书文档；手机飞书里发消息能让电脑上的小伴干活并回报结果。

## 5. 更多消息通道

- **企业微信**：有报道称企业微信 5.0.10 向所有企业开放 CLI 与 MCP，可调文档、日程、会议、邮件等（单一来源，需以腾讯官方为准）。思路同飞书。
- **QQ**：QQ 开放平台支持个人主体入驻，需实名认证，机器人需审核，可在单聊、群聊使用（以官方文档为准）。适合个人与年轻用户。不要用 NapCat 等非官方协议端。
